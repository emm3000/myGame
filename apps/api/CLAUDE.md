# apps/api

Hono on Node: the HTTP adapters, the persistence adapters that implement the domain ports, auth, and the composition root.

## Commands

- `API_PORT=3106 pnpm --filter @mygame/api dev` — `tsx watch src/server.ts`. Use the port the dispatch assigns, never a default. Add `SESSION_COOKIE_SECURE=false` when a browser reaches the api over plain `http://localhost`: Safari refuses a `Secure` cookie there.
- `pnpm --filter @mygame/api build` — esbuild bundles `src/server.ts` into one ESM file, `dist/server.js`: the workspace packages and `zod` are inlined, `hono`, `@hono/node-server`, `pg`, `drizzle-orm`, `@node-rs/argon2` and `nodemailer` stay external imports. A new runtime dependency gets its own `--external:` in the script.
- `API_PORT=3106 DATABASE_URL=... SMTP_URL=... MAIL_FROM=... WEB_URL=... pnpm --filter @mygame/api start` — `node dist/server.js`, the production entry. `/health` answers without a reachable database. CI builds and probes it after the gate.
- `pnpm --filter @mygame/api test` — Vitest, `src/**/*.test.ts`. Route tests compose the real server on the session's Postgres, with the real adapters; an in-memory adapter exists only to run a port's contract suite beside the Drizzle one.
- `pnpm --filter @mygame/api typecheck` — `tsc --noEmit` over `src`, the Vitest config and `drizzle.config.ts`.
- `pnpm --filter @mygame/api db:generate --name <change>` — `drizzle-kit generate`: diffs `src/adapters/postgres/schema.ts` against `migrations/meta` and writes the next SQL migration. Commit the SQL and the `meta` files together.
- `pnpm --filter @mygame/api db:migrate` — `drizzle-kit migrate`: applies pending migrations to `DATABASE_URL`.
- `pnpm gate` from the repo root before every commit.

## Local database

Postgres 18 in Docker, one container and one host port per session, never a system service and never the owner's database. The container is named `mygame-<session>-pg`, the database `mygame_<session>`, and the dispatch assigns the port:

```
docker run -d --name mygame-schema-pg -e POSTGRES_PASSWORD=mygame -e POSTGRES_DB=mygame_schema -p 5433:5432 postgres:18
export DATABASE_URL=postgres://postgres:mygame@localhost:5433/mygame_schema
```

`DATABASE_URL` must be set in the shell that runs `pnpm gate`; the migration test fails without it. CI runs the same image as a service container of the `gate` job.

## Local mail

Mailpit in Docker beside the Postgres one, one container and two host ports per session, the ports assigned by the dispatch. The container is named `mygame-<session>-mail`; the tag is the one `.github/workflows/ci.yml` pins, never `latest`:

```
docker run -d --name mygame-schema-mail -p 1033:1025 -p 8033:8025 axllent/mailpit:v1.31.3
export SMTP_URL=smtp://127.0.0.1:1033
export MAILPIT_URL=http://127.0.0.1:8033
export MAIL_FROM='myGame <no-reply@mygame.local>'
export WEB_URL=http://localhost:3233
```

`composeServer` refuses to compose without `SMTP_URL` (an `smtp:` or `smtps:` URL), `MAIL_FROM` or `WEB_URL` (an `http:` or `https:` URL, the web origin the mail links start from). `MAILPIT_URL` is read only by the `SmtpMailer` contract run, which reads the delivered mail back through Mailpit's HTTP API (`GET /api/v1/messages`, `GET /api/v1/message/<ID>`, `DELETE /api/v1/messages`). `pnpm gate` reads only `SMTP_URL` and `MAILPIT_URL` from the shell; the tests take `MAIL_FROM` and `WEB_URL` from `mailEnvironment` in `src/composeServer.testSupport.ts`. `dev` and `start` need `SMTP_URL`, `MAIL_FROM` and `WEB_URL`. CI runs the same image as a second service container of the `gate` job.

## Layout

- `src/app.ts` exports `createApp(dependencies)`, the Hono app with every route. Tests build it with `createApp({ ...server, clock, mailer })` over a composed server, swapping the clock and the mailer, and call `app.request(...)`; no socket.
- `src/composeServer.ts` is the composition root: the only module that constructs an adapter and wires it to a port. It reads `API_PORT` and refuses to compose unless it is an integer from 1 to 65535, and refuses to compose without `DATABASE_URL`. It reads `SESSION_COOKIE_SECURE`: unset or `true` marks the session cookie `Secure`, `false` drops the flag for a plain-http dev host, and any other value refuses to compose. It exposes the app's dependencies, `fiefs`, a lock-free `DrizzleFiefRepository` typed as the read-only `FiefReader` (`src/fief/FiefReader.ts`, the port without `save`, so a write that skips the row lock does not compile), and `inTransaction(work)`, which runs `work` inside one Drizzle transaction with a locking `DrizzleFiefRepository`, a `DrizzleChronicle`, a `DrizzleAccounts` and a `DrizzleAccountTokens` bound to it (`TransactionStores`: `fiefs`, `chronicle`, `accounts`, `accountTokens`). `work` returns a `Result`; a refusal rolls the whole transaction back. Every fief mutation and every sign-up goes through `inTransaction`.
- `src/composeServer.ts` also exposes `chronicle`, a lock-free `DrizzleChronicle` typed as `ChronicleReader`.
- `src/composeServer.ts` also exposes `mailer`, an `SmtpMailer` typed as `Mailer`, and `webUrl`. It is the only module that constructs a mailer, and it passes `mailer` and `webUrl` to `createApp`; sign-up and the verification resend send the verification mail. `src/auth/Mailer.ts` is the port: `send(mail)` takes a `Mail` (`to`, `subject`, `text`) and answers a `MailDelivery`, `sent` or `failed`. `src/adapters/smtp/SmtpMailer.ts` sends over `nodemailer` from `MAIL_FROM` through a plain `SMTPTransport`, never the pool, so the api keeps no idle socket or timer (N2), with a 3 s connection, 2 s greeting and 3 s socket timeout, so a server that accepts and stays silent cannot hold a request for nodemailer's default minutes, and answers `failed` instead of throwing when the server refuses or cannot be reached. `src/adapters/memory/MemoryMailer.ts` keeps what it sent and `MemoryMailer.failing()` answers `failed`; `src/adapters/mailerContract.ts` is the suite both run. `src/composeServer.testSupport.ts` holds the mail variables every test that composes a server spreads in.
- `src/server.ts` is the listener: it hands the composed server to `@hono/node-server` and does nothing else.
- `src/adapters/postgres/schema.ts` holds the Drizzle tables: `players` (since migration 0010 with the nullable `email_verified_at`, null until the email is verified, with no backfill, so every player stored before it is unverified), `sessions`, `account_tokens` (since migration 0010: `token_digest` primary key under the check `account_tokens_token_digest_hex`, which refuses anything but 64 lowercase hex digits, `player_id` cascading on the player's deletion, `kind` over the enum `account_token_kind` (`reset`, `verify`), `expires_at`, nullable `used_at`), `fiefs` (the five amounts, one `stored_at`, the nullable slot columns of the build slot (`slot_building`, `slot_level`, `slot_started_at`, `slot_finishes_at`) and the five `slot_cost_*` columns (`slot_cost_wood`, `slot_cost_stone`, `slot_cost_iron`, `slot_cost_gold`, `slot_cost_food`), `NOT NULL DEFAULT 0`, which hold the cost a busy slot debited and zeros on an idle one; since migration 0008 also the nullable study slot columns (`study_art` over the enum `art`, `study_level`, `study_started_at`, `study_finishes_at`) and the five `study_cost_*` columns, `NOT NULL DEFAULT 0`, written by `studyColumnsOf`, which refuses a half-written study row the way `slotOf` does), `fief_buildings` (over the enum `building`, which has `library` since migration 0007 and `barracks` since migration 0011) and `fief_queue_entries` (one row per waiting entry of the build queue, keyed by `(fief_id, position)`, with `building`, `target_level`, the five `cost_*` columns and `duration_seconds`, cascading on the fief's deletion), `fief_arts` (one row per studied art, keyed by `(fief_id, art)` over the enum `art`, with `level`, cascading on the fief's deletion), `fief_units` (since migration 0012: one row per unit kind with a count, keyed by `(fief_id, kind)` over the enum `unit` (`infantry`), with `count` under the check `fief_units_count_whole` (from 0), cascading on the fief's deletion; a kind without a row counts 0), `fief_recruit_orders` (since migration 0012: the open recruit order, `fief_id` its primary key, so one order per fief, cascading on the fief's deletion, `kind` over the enum `unit`, `count` under `fief_recruit_orders_count_positive` (from 1), the five `cost_*` it debited, `per_unit_seconds` under `fief_recruit_orders_per_unit_seconds_positive` (from 1), `started_at`; no row is an idle recruit slot), `fief_marches` (since migration 0014: the away march, `fief_id` its primary key, so one march per fief, cascading on the fief's deletion, `province`, `plot`, `infantry` and `one_way_seconds` integers each under a `fief_marches_<column>_positive` check (from 1), `stay_hours`, `departed_at`, the five `loot_*` fixed at dispatch, each under `fief_marches_loot_<resource>_whole` (a whole amount from 0), since migration 0015 a nullable `recalled_at` under `fief_marches_recalled_after_departure` (null, or at or after `departed_at`), null on every march stored before it, so it reads unrecalled with no backfill, and since migration 0016 `march_order` over the enum `march_order` (`forage`, `attack`), `NOT NULL DEFAULT 'forage'`, the nullable `camp_tier` and `camp_strength` of the camp snapshot read at dispatch and `fought` `NOT NULL DEFAULT false`; the check `fief_marches_order_terms`, which replaced `fief_marches_stay_hours_positive` in migration 0016, takes a forage row with `stay_hours` from 1, no camp and `fought` false, or an attack row with `stay_hours` 0, a `camp_tier` from 1 to 3 and a `camp_strength` from 0, so every march stored before it reads as a forage march with no backfill; no row is an idle march slot), `camp_battles` (since migration 0016: identity `id`, `kingdom`, `province` and `plot` each under a `camp_battles_<column>_positive` check (from 1), `strength` under `camp_battles_strength_whole` (from 0), `fought_at`, index `camp_battles_plot_order` on the address, `fought_at` and `id`; one row per battle, insert-only and never pruned, with no foreign key, since a camp's state outlives any fief) and `fief_events` (since migration 0009: identity `id`, `fief_id` cascading on the fief's deletion, `kind` over the enum `fief_event_kind` (`recruits_delivered` since migration 0012, `recruits_cancelled` since migration 0013, `march_returned` since migration 0014), nullable `building` and `art` over the existing enums, since migration 0012 a nullable `unit` over the enum `unit` and a nullable `count`, since migration 0013 a nullable `cancelled_count`, since migration 0014 a nullable `province` and `plot`, since migration 0015 `recalled` `NOT NULL DEFAULT false` under the check `fief_events_recalled_only_march` (only a `march_returned` row holds `true`), so every row stored before it reads `false`, `level` nullable since migration 0012, five `refund_*` `NOT NULL DEFAULT 0`, `occurred_at`; the check `fief_events_one_subject`, which replaced `fief_events_building_or_art` in migration 0012, takes exactly one of `building`, `art` and `unit`, a `level` on a building or art row only and a `count` on a unit row only, and since migration 0013, which replaced it, a `cancelled_count`, from 1, on a unit row only, and since migration 0014, which replaced it again, `province` and `plot` both null or both from 1 on a unit row only, so every row stored before it reads as before; a recruits-cancelled row holds the delivered units in `count`, the cancelled units in `cancelled_count` and the refund in the five `refund_*`; a march-returned row is a unit row (`unit` `infantry`) holding the infantry in `count`, the target in `province` and `plot` and the loot in the five `refund_*`; it does not tie `kind` to the subject, since a migration may not use the enum value it adds; index `fief_events_fief_order`). No rate, capacity or peasant count is stored (ADR 005, ADR 007).
- `src/adapters/postgres/DrizzleFiefRepository.ts` implements `FiefRepository`. `fiefOf` is one query: the fief row left-joined to its level rows, its queue entries, its art rows, its unit rows, its recruit order and its march. The joins multiply the rows (levels × entries × arts × units; the order and the march are at most one row each), so the mapper deduplicates levels by building, entries by position, arts by art and units by kind, then orders the entries by position; the order and the march come from the first row. With `'lockedForUpdate'` it takes `FOR UPDATE OF fiefs`; with `'lockFree'` it takes no lock, so a read never queues behind a mutation. `save` runs one transaction, a savepoint inside `inTransaction`: it upserts the fief row, its built level rows, its studied art rows and its unit rows with a count above 0, deletes the unit row of every kind whose count is 0, so a count that drops to 0 reads back as 0, replaces its queue entries (delete, then insert at positions 0..n−1), replaces its recruit order (delete, then insert when one is open) and replaces its march (delete, then insert when a march is away, with `recalled_at` null unless the march holds `recalledAt`; a forage march with `march_order` `forage`, no camp and `fought` false, an attack with `march_order` `attack`, its `camp` in `camp_tier` and `camp_strength` and its `fought`). It restores a `march_order` `attack` row as an attack march and throws on one whose camp columns are null or whose tier is outside 1..3, as it does on a half-written slot. A building without a row is unbuilt; an art without a row is at level 0; a unit kind without a row counts 0.
- `src/adapters/postgres/DrizzleChronicle.ts` implements `ChronicleWriter` and `ChronicleReader` (`src/fief/ChronicleReader.ts`, `eventsOf(fiefId)`, newest `occurred_at` first, a tie newest `id` first, at most `keptEventsPerFief` = 100). `rowOf` and `eventOf` switch exhaustively over the event kinds, and they alone tie a kind to its columns (`recruitsCancelled` to `unit`, `count` as `delivered`, `cancelled_count` as `cancelled` and `refund_*`; `marchReturned` to `unit` `infantry`, `count` as `infantry`, `province`, `plot`, `recalled` and `refund_*` as `loot`). `record` inserts, then deletes the fief's rows beyond the latest 100 on the same session; with no events it does nothing. `src/adapters/memory/MemoryChronicle.ts` is the in-memory one; `src/adapters/chronicleContract.ts` is the suite both run. The chronicle is never joined into the fief read. `src/adapters/postgres/storedKinds.ts` holds the building, art and unit enum maps both postgres adapters share.
- `src/adapters/json/JsonBuildingCatalog.ts` implements `BuildingCatalog` from `content/`: one JSON per building (seven, `library.json` and `barracks.json` included; the barracks at levels 1 to 10 from 200 wood, 120 stone, 60 iron, 360 s and 1 peasant, with no effect), `fief.json` for the settings (its `seasons` holds the `epoch` ISO instant, which the adapter hands to the domain as an `Instant`, `daysPerSeason`, `multiplierPercent`, a whole percent from 1 per season and resource, and `durationPercent`, a strict `{ build, study, train }` of whole percents from 1 per season; the shipped content has `summer.build` 75, `winter.study` 75, `spring.train` 75 and every other cell 100; its `units` carries, per `UnitKind`, a `cost`, a `durationSeconds`, a `peasantOccupancy` and a `strength`, whole counts from 1: infantry at 20 wood, 10 iron, 30 food, 90 s, 1 peasant, strength 1), and `content/arts/smithing.json` and `content/arts/masonry.json` parsed with `ArtContentSchema`. It fails at start-up on a malformed file or on an art file that names the other art.
- `fief.json`'s `forage` carries 600 s per province, 60 s per plot, a carry of 48 per infantry, a longest stay of 8 h and `yieldPerHour` per terrain (3 on lowlands food and wood, uplands wood and stone, ridges stone and iron, gold always 0); `FiefContentSchema` refuses a gold rate above 0 and the api does not start.
- `fief.json`'s `camps` carries `campFraction` 0.2 (a number from 0 to 1), `lootPerStrength` 60 and `tiers` keyed `1`, `2` and `3`, each a `{ maxStrength, regrowHours }` of whole counts from 1: 6 in 6 h, 15 in 12 h and 40 in 24 h. A missing tier or field, or a fraction above 1, fails the parse and the api does not start. The adapter's `...fief` spread hands it to the domain as `FiefSettings.camps`. Changing `campFraction` moves every camp, a content edit, as `plotsPerProvince` does (ADR 014).
- `src/adapters/memory/MemoryFiefRepository.ts` is the in-memory `FiefRepository`. `src/adapters/fiefRepositoryContract.ts` is the port's contract suite, and both adapters' tests run it.
- `src/adapters/postgres/DrizzleCampRegistry.ts` implements the domain's `CampRegistry` over `camp_battles`, one query per method on the session it is built with: `lastBattleOf` the plot's row with the latest `fought_at`, a tie read by the highest `id`, the latest insert; `lastBattlesIn` one such row per plot of a kingdom's province through `DISTINCT ON (plot)`, ordered by plot; `record` inserts. `src/adapters/memory/MemoryCampRegistry.ts` is the in-memory one; `src/adapters/campRegistryContract.ts` is the suite both run. Nothing composes it yet: the registry reaches the composition root in #299 (the transaction) and #301 (the pool).
- `src/adapters/postgres/DrizzleKingdomMapReader.ts` implements `KingdomMapReader` over the address columns of `fiefs`, with one lock-free query per method: `addressOf` by `player_id`, `lastOccupiedProvince` as `max(province)` of the kingdom (0 when none), and `holdersIn` as the fiefs of one kingdom and province ordered by `plot`. `src/adapters/memory/MemoryKingdomMapReader.ts` reads the fiefs a `MemoryFiefRepository` holds through `heldFiefs()`. `src/adapters/kingdomMapReaderContract.ts` is the suite both run, seeded through the `FiefRepository` of the same store.
- `src/adapters/system/` holds `SystemClock`, the only file that calls `Date.now()`, `CryptoIdGenerator`, which issues uuids, `CryptoSessionTokens`, which issues 256-bit base64url session tokens, and `Argon2Passwords`, which hashes with Argon2id at explicit cost (19456 KiB, 2 passes, 1 lane; a test asserts the encoded parameters, since the library's `Algorithm` is an ambient const enum that `verbatimModuleSyntax` refuses, so the algorithm itself is the library default and pinned by that test) and verifies an unknown email against a decoy hash so both refusals cost the same.
- `src/adapters/postgres/DrizzleAccounts.ts` implements `Accounts` (`src/auth/Accounts.ts`) over players and sessions. The api has four ports of its own: `Accounts`, since auth is not a domain concern, so its persistence port lives beside the auth flows that depend on it; `AccountTokens` (`src/auth/AccountTokens.ts`) beside it for the same reason; `ChronicleReader` (`src/fief/`), since the domain never reads the chronicle; and `Mailer` (`src/auth/Mailer.ts`), since no use case of the domain sends a mail. The session token is never stored: `sessions.token_digest` holds `tokenDigest(token)` (`src/auth/tokenDigest.ts`, the lowercase hex SHA-256 of its UTF-8 bytes), and `openSession`, `renewSession` and `closeSession` digest the token before they touch the row, so a leak of that table is disclosure, not impersonation. The cookie still carries the plain token. The check `sessions_token_digest_hex` refuses anything but 64 lowercase hex digits. A plain SHA-256 suffices, with no salt or slow hash, because the token is 256 random bits.
- `src/adapters/postgres/DrizzleAccountTokens.ts` implements `AccountTokens` over `account_tokens`, storing `tokenDigest(token)`, never the plain token. `issue(token, now)` deletes the player's tokens of that kind and each of the player's used or expired tokens, then inserts, so pruning happens on the next issue for the same player and nothing prunes on a timer. `redeem(token, kind, now)` is one `UPDATE ... SET used_at = now WHERE` digest, kind, `used_at IS NULL` and `expires_at > now` `RETURNING player_id`, so two redeems of one token answer one player. `src/auth/accountTokenExpiryFrom.ts` gives a `reset` token 1 hour and a `verify` token 24 hours. `src/adapters/memory/MemoryAccountTokens.ts` is the in-memory one; `src/adapters/accountTokensContract.ts` is the suite both run. Sign-up and the verification resend issue `verify` tokens. `issue` runs in its own transaction (a savepoint inside `inTransaction`) and first locks the player's row with `SELECT ... FOR NO KEY UPDATE`, so two racing issues serialize without blocking the `FOR KEY SHARE` of a session insert, and leave one live token of a kind; the contract suite's `issueTogether` fixture holds the first transaction open until the second issue waits on that lock. `redeem` also locks the player with `FOR NO KEY UPDATE` inside a savepoint: it reads the live token to find the player, locks the player, then marks the token used, so `issue` and the redeems lock in the same order (player, then tokens) and a redeem racing an issue cannot deadlock.
- `src/auth/` also holds `issueAccountToken(kind, playerId, deps)` (a `CryptoSessionTokens` token with the kind's expiry, issued through the transaction's `accountTokens`), `sendVerificationMail` (link `<WEB_URL>/verify-email?token=<token>`, copy from `src/mail/mailCopy.ts`), `verifyEmail` and `resendVerificationMail`. Sign-up issues the verify token inside its transaction and sends the mail after commit, ignoring a failed send. `src/mail/mailCopy.ts` mirrors the mail lines of `docs/lore/names.md` and is the second Spanish file of the api, after `answerRefusal.ts`. `Accounts.StoredPlayer` carries `emailVerified`, read as `email_verified_at IS NOT NULL`; `markEmailVerified(playerId, now)` sets `email_verified_at`. `requestPasswordReset` reads `credentialsOf(email)` in a transaction and issues a `reset` token only for a verified player, then sends `mailCopy.reset` with `<WEB_URL>/reset-password?token=<token>` after commit and ignores a failed send. `resetPassword` hashes before `inTransaction`, then redeems the `reset` token, calls `storePasswordHash` and `closeSessionsOf` in one transaction. `Accounts` gains `storePasswordHash(playerId, hash)` and `closeSessionsOf(playerId)`.
- `src/routes/auth.ts` also serves `POST /auth/verify-email` (no session; 204, 400 `TokenInvalid` for an unknown, expired, used or `reset` token, 400 with an empty body for a malformed one) and `POST /auth/verify-email/resend` behind `requirePlayer` (204; 204 with no mail once verified; 503 `MailNotSent` when the send fails). Sign-up, sign-in and `GET /auth/session` answer `emailVerified`, mapped field by field. `answerRefusal` also maps `TokenInvalid` (400) and `MailNotSent` (503). It also serves `POST /auth/forgot-password` (no session; 202 empty for any well-formed email, 400 empty for a malformed one) and `POST /auth/reset-password` (no session; 204 with no cookie, 400 `TokenInvalid` for an unknown, expired, used or `verify` token, 400 `WeakPassword` for a password under 8 characters before any store call, 400 empty for a body without a token).
- `src/auth/` holds `signUp`, `signIn` and `foundFiefOnFreePlot`. Sign-up hashes the password, then in one `inTransaction` inserts the player, founds the fief and opens the session. `foundFiefOnFreePlot` retries `foundFief` up to three times on `CoordinatesTaken`: a racing sign-up that took the plot has committed by then, so the retry picks the next free plot, and a second founding for one player ends as `PlayerAlreadyHoldsFief`.
- `src/http/requirePlayer.ts` is the only reader of the session cookie. It renews the session row to now + 30 days in one `UPDATE ... WHERE expires_at > now RETURNING`, rewrites the cookie and yields `playerId` and `sessionToken` in `c.var`; without a live session it answers 401.
- `src/http/answerRefusal.ts` is the one module that maps a `Refusal` (every `DomainError` kind plus the api's `EmailTaken`, `InvalidCredentials`, `WeakPassword`, `MalformedRequest`, `SignedOut`) to a status and, for the kinds `ApiErrorSchema` knows, the Spanish message. A kind the wire does not name answers its status with an empty body.
- `src/routes/auth.ts` serves `POST /auth/sign-up` (201 `Player`), `POST /auth/sign-in` (200 `Player`), `POST /auth/sign-out` (204) and `GET /auth/session` (200 `Player`). The cookie is `session`, `HttpOnly; Secure; SameSite=Lax; Path=/`, 30 days; `Secure` follows `SESSION_COOKIE_SECURE`.
- `src/routes/fief.ts` serves `GET /fief` (200 `FiefOverview`) behind `requirePlayer`: the signed-in player's one fief, never another's. `src/fief/currentFiefOf.ts` runs `resolveUpgrade` over the lock-free reader with a dry-run `save` and a discarding chronicle at one frozen `now`; only its `inTransaction` rerun records the finish events on the transaction's chronicle; only when that reports `hasChanged` (a busy build or study slot whose finish has passed; the walk then applies every finished upgrade and the finished study, in the order they finished) does it rerun `resolveUpgrade` inside `inTransaction`, where the locked read re-decides and persists. The fief comes back accrued to `now`, or to its `storedAt` when a concurrent write stored it at a later instant than the read's `now` (two reads racing on one finished slot, or an enqueue committing mid-read), so a plain read never answers `InstantBeforeStored`. `src/fief/fiefOverviewOf.ts` maps it to the wire through the domain's `derive*` functions. Each building answers its `level` and its `nextLevel`: `null` when the `BuildingCatalog` has no `level + 1`, otherwise that level's cost, its duration scaled by `deriveBuildDurationSeconds` with the build percent of `durationPercentAt` at `storedAt`, so a read and an enqueue at one instant agree, and its `peasants`, `derivePeasantsForUpgrade`, the same increase in occupancy the enqueue charges, never the raw occupancy; `nextLevel` follows the projected level (the built level with the busy slot and every waiting entry applied), so a building waiting twice answers the level after both. `peasants.projectedSupplied` and `peasants.projectedOccupied` are the supply and occupancy of the projected levels, and `peasants.projectedFree`, their difference, is what the enqueue checks against. `queue.cap` is the catalog's `buildQueueCap`; `queue.entries` lists the waiting entries from the domain's `scheduleBuildQueue`: the first starts at the slot's `finishesAt`, each next one at the previous `finishesAt`; behind an idle slot it is empty. `readAt` is the fief's `storedAt` after that accrual. `season` is what the domain's `seasonAt` answers for that same `storedAt`: `null` before the content's epoch, otherwise its `kind`, `year`, `endsAt` through `isoOf`, the content's `multiplierPercent` for that season, and its `durationPercent`, the `{ build, study, train }` of `durationPercentAt` at that same `storedAt`, read once and handed to both `seasonOf` and `recruitTermsOf`; each `ratePerHour` is `deriveResourceRates` at the same instant and every `nextLevel.durationSeconds` is scaled by that same `durationPercentAt`, so the season answered, the rates and the durations never disagree. A read with nothing to resolve is one query after the session renewal, asserted in `src/routes/fief.test.ts` by spying on `pg`'s `Client.prototype.query`.
- `src/routes/fief.ts` also serves `GET /fief/events` (200 `FiefChronicle`) behind `requirePlayer`. It runs `currentFiefOf` first, so a finish that no read has applied yet is written and listed, then answers `chronicle.eventsOf(fief.id)` through `src/fief/fiefChronicleOf.ts`, newest first. `wireEventOf` answers the `recalled` the domain event and its column carry. With no fief it answers 404 `FiefNotFound`. The read is the fief read plus one query for the events.
- `src/routes/map.ts` serves `GET /map` (the viewer's own province) and `GET /map/:province` behind `requirePlayer` (200 `ProvinceMap`). Each runs `readProvinceMap` over `map`, the one lock-free `DrizzleKingdomMapReader` that `composeServer` builds. It resolves no fief and opens no transaction: the session renewal plus three queries. `src/kingdom/provinceMapOf.ts` maps the domain `ProvinceMap` to the wire field by field, with a free plot as `null`. A malformed province answers 400, a province beyond `lastProvince` 404 `ProvinceNotFound`, and a player without a fief 404 `FiefNotFound`.
- `src/routes/fief.ts` also serves `POST /fief/upgrades` (200 `FiefOverview`) behind `requirePlayer`: the body parses with `EnqueueBuildingRequestSchema` (a failed parse answers `MalformedRequest`, 400). `src/fief/mutateAfterResolve.ts` is the one place that locks the fief, takes the instant clamped to its `storedAt` (so a write that committed while the call waited on the lock answers its true refusal, never `InstantBeforeStored`), and runs `resolveUpgrade` before a mutation, all in one `inTransaction`; `enqueueUpgradeOf`, `cancelUpgradeOf`, `startStudyOf` and `cancelStudyOf` each pass their use case to it as a callback. It answers a `Fief`; `cancelUpgradeOf` and `cancelStudyOf` read `.fief` from the `ChangedFief` their use case answers. `FiefMutation` takes `{ fiefs, chronicle }` and the clock; the resolve and the cancels record their events on the transaction's chronicle, so a refusal rolls them back with the rest. `src/fief/enqueueUpgradeOf.ts` runs `enqueueBuilding` that way, so a slot whose finish has passed is completed before the new upgrade starts, and a refusal rolls back the resolve too. With the slot busy the upgrade joins the build queue; at `buildQueueCap` waiting entries it answers `QueueFull`, 409. The answered overview goes through `fiefOverviewOf`; each refusal goes through `answerRefusal`.
- `src/routes/fief.ts` also serves `DELETE /fief/upgrades/:building/:targetLevel` (200 `FiefOverview`) behind `requirePlayer`, the path parsed by `CancelUpgradeRequestSchema` (an unknown building or a target level that is not a whole count from 1 answers 400). `src/fief/cancelUpgradeOf.ts` runs `cancelUpgrade` through `mutateAfterResolve`, so an entry that finished before the cancel, or that the queue no longer holds, answers `UpgradeNotFound`, 409.
- `src/routes/fief.ts` also serves `POST /fief/studies` (200 `FiefOverview`) behind `requirePlayer`: the body parses with `StartStudyRequestSchema` (a failed parse answers `MalformedRequest`, 400). `src/fief/startStudyOf.ts` runs `startStudy` through `mutateAfterResolve`; `StudySlotBusy`, `LibraryLevelTooLow` and `ArtMaxLevelReached` answer 409. `fiefOverviewOf` answers `study` and `arts`: `ratePercent` is 0 at level 0 and otherwise the line in force, read through `artLevelInForce`; `arts[art].resource` comes from the domain's `artResourceOf`, so it is answered at level 0 too; `arts[art].nextLevel` follows the built art level, not a projection of the running study, unlike `buildings[building].nextLevel`, and its `durationSeconds` is already shortened by the built library and scaled by the study percent of `durationPercentAt` at `storedAt`, through `deriveStudyDurationSeconds`.
- `src/routes/fief.ts` also serves `DELETE /fief/studies/:art/:targetLevel` (200 `FiefOverview`) behind `requirePlayer`, the path parsed by `CancelStudyRequestSchema` (else 400). `src/fief/cancelStudyOf.ts` runs `cancelStudy` through `mutateAfterResolve`: a study finished by the clamped instant is applied by the resolve, then the cancel answers 409 `StudyNotFound` and the refusal rolls the transaction back, so the next read persists the finish.
- `src/routes/fief.ts` also serves `POST /fief/recruit-orders` (200 `FiefOverview`) behind `requirePlayer`: the body parses with `PlaceRecruitOrderRequestSchema` (a failed parse answers `MalformedRequest`, 400). `src/fief/placeRecruitOrderOf.ts` runs `placeRecruitOrder` through `mutateAfterResolve`, so an order that ended by the clamped instant is closed first; `BarracksNotBuilt`, `RecruitSlotBusy`, `InsufficientResources` and `NotEnoughPeasants` answer 409. `fiefOverviewOf` answers `units` from `Fief.unitCountsAt(storedAt)` and `recruitOrder.delivered` from `deliveredUnitsOf` at the same instant, so the two never disagree; `recruitOrder.endsAt` is `recruitOrderEndsAt`; `recruitTerms[unit]` reads the unit's content, `perUnitSeconds` scaled by the `train` percent of the same `durationPercentAt` call `season` answers and divided by one plus the built barracks level through `deriveUnitDurationSeconds`, as a study's duration is divided by the built library; an open order answers its stored `perUnitSeconds`, the season it was placed in, even after another season begins.
- `src/routes/fief.ts` also serves `DELETE /fief/recruit-orders/:unit/:startedAt` (200 `FiefOverview`) behind `requirePlayer`, the path parsed by `CancelRecruitOrderRequestSchema` (else 400); Hono decodes the URL-encoded colons of `startedAt` before the parse. `src/fief/cancelRecruitOrderOf.ts` turns `startedAt` into an `Instant` and runs `cancelRecruitOrder` through `mutateAfterResolve`: an order that ended by the clamped instant is closed by the resolve, then the cancel answers 409 `RecruitOrderNotFound` and the refusal rolls the transaction back, so the next read persists the delivery. A start that names another order answers the same 409.
- `src/routes/fief.ts` also serves `POST /fief/marches` (200 `FiefOverview`) behind `requirePlayer`: the body parses with `DispatchMarchRequestSchema` (a failed parse answers `MalformedRequest`, 400 with an empty body). `src/fief/dispatchMarchOf.ts` takes the request type from `@mygame/contracts` and runs `dispatchMarch` through `mutateAfterResolve`, so a march that returned by the clamped instant is closed first and frees the slot; it passes `map`, the lock-free `DrizzleKingdomMapReader` `composeServer` builds, beside the transaction's stores and never inside `TransactionStores` (ADR 014: a plain read of `fiefs` does not wait on the fief's `FOR UPDATE`). `PlotHeld`, `PlotHasCamp` (a forage march to a camp's plot), `MarchToOwnPlot`, `NotEnoughInfantryAtHome`, `MarchSlotBusy`, `StayOutOfRange` and `MarchTargetOutOfBounds` answer 409 with the lines of the marches and camps sections of `docs/lore/names.md`; `PlotHasNoCamp` answers 409 too, with no route before #302; an infantry count below 1 never reaches the use case, since the schema refuses it. `fiefOverviewOf` answers `march` from the stored away march with the target's `terrainOf(province)` and the `arrivesAt`, `leavesAt` and `returnsAt` of `marchInstantsOf`, `recalledAt` the stored recall or `null`, no phase; `units` still counts the infantry away. `forageTerms` copies `forage` of the content field by field, `gold` 0 in every yield.
- `src/routes/fief.ts` also serves `POST /fief/marches/:departedAt/recall` (200 `FiefOverview`) behind `requirePlayer`, the path parsed by `RecallMarchRequestSchema` (else 400 `MalformedRequest` with an empty body); Hono decodes the URL-encoded colons of `departedAt` before the parse. `src/fief/recallMarchOf.ts` takes the request type from `@mygame/contracts`, turns `departedAt` into an `Instant` and runs `recallMarch` through `mutateAfterResolve`: a march that returned by the clamped instant is closed by the resolve, then the recall answers 409 `MarchNotFound`, as a departure that names another march does; a march already returning answers 409 `MarchAlreadyReturning`. Each refusal rolls the transaction back, so the next read persists the return.
- `migrations/` holds the generated SQL and drizzle-kit's `meta` snapshots. A migration is never edited after it merges; a change is a new migration.

## Gotchas

- Routes stay thin: parse with the contract schema, call the use case, map the `Result`. No rule lives in a route.
- Adapters implement ports defined in `@mygame/domain`; the four api-side exceptions are `Accounts`, `AccountTokens` and `Mailer` in `src/auth/`, since auth stays out of the domain, and `ChronicleReader` in `src/fief/`, since the domain never reads the chronicle.
- No `nodemailer` import outside `src/adapters/smtp/`. nodemailer 10 ships its own types, so no `@types/nodemailer`.
- Point `SMTP_URL` at `127.0.0.1`, not `localhost`: nodemailer resolves a host name through `dns.resolve4` before it falls back to `dns.lookup`, and on macOS that query for `localhost` can stall the first send for about 5 s, past Vitest's timeout.
- Mailpit's `Text` ends with the line break that closes the SMTP body; the contract run strips one trailing `\r\n` before comparing.
- A write through a store not bound to the `inTransaction` transaction that touches a row referencing `fiefs` blocks on the fief's `FOR UPDATE` lock (the foreign key takes `FOR KEY SHARE`); every store inside `work` must come from `TransactionStores`.
- No Drizzle import outside an adapter.
- Every mutation of a fief runs in one transaction that first locks the fief row with `SELECT ... FOR UPDATE`, then materializes, applies and writes (N4, ADR 006). Two concurrent mutations serialize on that lock.
- The migration test applies every migration inside one transaction after dropping `public` and `drizzle`, and rolls back, so it sees an empty database and leaves the session's database as it found it.
- Drizzle's `insert` lists every column of the current `schema.ts` and sends `default` for any that is missing, so `db.insert(fiefs)` fails on a database at an older migration. A migration test seeds the previous version's rows with `client.query` and plain SQL.
- `vitest.globalSetup.ts` applies `migrations/` to `DATABASE_URL` before the suite, so a fresh database (CI's service container) has the tables. The api test files share that database and truncate it, so `vitest.config.ts` sets `fileParallelism: false`.
- The `fiefs.terrain` column is written from `Fief.terrain` and never read back: the domain derives terrain from the province.
- The race test in `composeServer.test.ts` races two sawmill enqueues and asserts both succeed, the second queued behind the first at level 2, with both costs debited; without the row lock both read the idle slot and the second overwrites the first. It pauses the first transaction after its read. It resumes once the second transaction's fief read (`select "fiefs"."id", ...`) shows up as waiting on a lock in `pg_stat_activity`, or once the second has read. The probe matches the start of the query, not its `for update of "fiefs"` tail: `pg_stat_activity.query` keeps only `track_activity_query_size` bytes (1 kB by default), and the read with all its joins is longer than that. The probe is bounded. With the lock removed the test fails every time.
- A table that references `players` or `fiefs` joins every `TRUNCATE` list in the api tests that truncates the table it references.
- The content copies in `composeServer.test.ts` must include `arts/`: they use `cpSync` recursive and `mkdirSync` for `arts`, and the minimal content must include `library.json` and `barracks.json`.
- Drizzle runs every pending migration of one `db:migrate` in one transaction, and Postgres refuses to use a value that `ALTER TYPE ... ADD VALUE` added in the same transaction unless the type was created there too. The migration test gets away with it because migration 0001 creates `building` in that transaction; a migration must never use a value that it, or an earlier migration of the same run, adds.
- `db:generate` needs `DATABASE_URL` set, because `drizzle.config.ts` refuses to load without it, even though generate never connects.
- `fiefs_player_unique` holds one fief per player; `save` maps its violation to `PlayerAlreadyHoldsFief`. Two foundings that race for one player also pick the same plot, and Postgres checks `fiefs_coordinates_unique` first, so the loser's first attempt reports `CoordinatesTaken`; `foundFiefOnFreePlot` retries it into `PlayerAlreadyHoldsFief`.
- The race tests in `src/auth/foundFiefOnFreePlot.test.ts` hold both transactions after their first `occupiedPlots` read until both have read, so both pick the same plot. With the retry removed both tests fail every time.
- A password shorter than 8 characters fails `SignUpRequestSchema` and `ResetPasswordRequestSchema`. Both routes map a `too_small` issue on `password` to `WeakPassword` and any other issue to `MalformedRequest` through `passwordRequestRefusalOf`.
- `pnpm add` in pnpm 11 ignores `save-exact` from `.npmrc` and writes a caret; fix the specifier by hand. `@node-rs/argon2` ships prebuilt binaries, so it needs no `allowBuilds` entry.
- No pepper or secret is configured: Argon2id salts each hash itself, so no auth env variable exists yet.
- The `fiefs_<resource>_whole` checks refuse a stored amount that is fractional or negative.
- Apply migration 0004 with every build slot idle and the api stopped. It adds the `slot_cost_*` columns with no backfill, because SQL cannot recover a running upgrade's cost from the JSON catalog, so a slot busy across it keeps cost 0 and its cancel would refund nothing.
- No check ties the `slot_cost_*` columns to `slot_building`: an idle row holds zeros only because `slotColumnsOf` writes them, and nothing refuses a negative stored cost but `Fief.restore`.
- Likewise no check ties `study_cost_*` to `study_art`, and nothing refuses a negative stored study cost but `Fief.restore`.
- `players_email_unique` is a unique index on `lower(email)`: the email is stored as typed and compared case-insensitively.
- `fief_events_recalled_only_march` compares `kind::text`, never the enum literal: a database at 0013 migrates 0014 and 0015 in one transaction, and Postgres refuses the uncommitted value `march_returned` cast to the enum ("unsafe use of new value"). A check that names an enum value added by a migration still unapplied somewhere compares the text.
- `fief_marches_order_terms` compares `march_order::text` too, though migration 0016 creates the enum, so no raw check has to reason about which run added which value. The column is `march_order`, never `order`, an SQL keyword a raw check would have to quote.
- `drizzle-kit generate` asks whether a new column renames an old one, and that prompt needs a TTY; a shell without one fails with "Interactive prompts require a TTY terminal". Run `db:generate --custom --name <change>` instead: it writes an empty SQL file, the journal entry and a snapshot copied unchanged from the previous one. Write the SQL by hand, edit the snapshot to match `schema.ts`, and confirm with `db:generate --name probe`, which must report no schema change and write no file.
- `drizzle-orm`, `pg` and `drizzle-kit` have one consumer, so their versions live here, not in the catalog.
- Import `@mygame/contracts` and `@mygame/domain` only from their entry; `rg -n "from '@mygame/(domain|contracts)/src" apps packages` stays empty.
- The workspace packages export raw `.ts` with extensionless relative imports, which plain `node` cannot load (`ERR_MODULE_NOT_FOUND`). Production runs the esbuild bundle, which inlines them; `dev` runs through `tsx`, which resolves them at runtime. `server.ts` finds `../content/` from `import.meta.url`, and `dist/` sits beside `src/`, so the bundle resolves the same directory.
- `hono`, `@hono/node-server`, `tsx` and `esbuild` have one consumer, so their versions live here, not in the catalog; `typescript` and `vitest` come from `catalog:`.
- `esbuild` (a devDependency here, and under `tsx`) is listed in `allowBuilds` in `pnpm-workspace.yaml`; pnpm 11 fails the install on an unreviewed build script.
