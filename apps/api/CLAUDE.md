# apps/api

Hono on Node: the HTTP adapters, the persistence adapters that implement the domain ports, auth, and the composition root.

## Commands

- `API_PORT=3106 pnpm --filter @mygame/api dev` — `tsx watch src/listen.ts`, the local Node listener. Use the port the dispatch assigns, never a default. Add `SESSION_COOKIE_SECURE=false` when a browser reaches the api over plain `http://localhost`: Safari refuses a `Secure` cookie there.
- `pnpm --filter @mygame/api build` — esbuild bundles `src/index.ts` into one ESM file, `dist/index.js`, the production entry Vercel runs (ADR 031): the workspace packages are inlined, `hono`, `pg`, `drizzle-orm`, `@node-rs/argon2`, `nodemailer`, `@hono/zod-openapi` and `zod` stay external imports, which Vercel's trace carries into the function. A new runtime dependency gets its own `--external:` in the script. `zod` is external because `@hono/zod-openapi` imports it from `node_modules`: an inlined copy beside it would be a second zod at runtime. `/health` answers without a reachable database; CI imports the bundle after the gate and asks its `fetch` for `/health`.
- `pnpm --filter @mygame/api test` — Vitest, `src/**/*.test.ts`. Route tests compose the real server on the session's Postgres, with the real adapters; an in-memory adapter exists only to run a port's contract suite beside the Drizzle one.
- `pnpm --filter @mygame/api typecheck` — `tsc --noEmit` over `src`, the Vitest config and `drizzle.config.ts`.
- `pnpm --filter @mygame/api openapi:write` — `tsx src/writeOpenApiDocument.ts`, then `biome format`: composes the server from the shell's environment (`DATABASE_URL`, `SMTP_URL`, `MAIL_FROM`, `WEB_URL`, as `dev`; nothing connects), asks it for `GET /openapi.json` and writes `openapi.json`, the committed copy the Android client is generated from. `src/openApi.test.ts` fails while the committed copy differs from what the app emits, so a declared schema edited without this command turns `pnpm gate` red.
- `pnpm --filter @mygame/api db:generate --name <change>` — `drizzle-kit generate`: diffs `src/adapters/postgres/schema.ts` against `migrations/meta` and writes the next SQL migration. Commit the SQL and the `meta` files together.
- `pnpm --filter @mygame/api db:migrate` — `drizzle-kit migrate`: applies pending migrations to `DATABASE_URL`.
- `pnpm gate` from the repo root before every commit.

## Local database

Postgres 18.6 in Docker (the exact tag `.github/workflows/ci.yml` pins), one container, one named volume and one host port per session, never a system service and never the owner's database. The container is named `mygame-<session>-pg`, its data volume `mygame-<session>-pgdata` (mounted at `/var/lib/postgresql`, the path the image declares as its volume), the database `mygame_<session>`, and the dispatch assigns the port:

```
docker run -d --name mygame-schema-pg -v mygame-schema-pgdata:/var/lib/postgresql -e POSTGRES_PASSWORD=mygame -e POSTGRES_DB=mygame_schema -p 5433:5432 postgres:18.6 -c fsync=off -c synchronous_commit=off -c full_page_writes=off
export DATABASE_URL=postgres://postgres:mygame@localhost:5433/mygame_schema
```

Without `-v` the image creates an anonymous volume that cannot be told apart from another project's once the container is gone; the named one lets `scripts/mygame-wave-close` remove it and `scripts/mygame-orphans` report it. The three `-c` flags drop durability, which holds only test data: a crash may lose or corrupt it and the container is recreated, so never on Neon or any database whose data matters. `DATABASE_URL` must be set in the shell that runs `pnpm gate`; the migration test fails without it. CI runs the same image as a service container of the `gate` job, with the same three settings.

## Local mail

Mailpit in Docker beside the Postgres one, one container and two host ports per session, the ports assigned by the dispatch. The container is named `mygame-<session>-mail`; the tag is the one `.github/workflows/ci.yml` pins, never `latest`:

```
docker run -d --name mygame-schema-mail -p 1033:1025 -p 8033:8025 axllent/mailpit:v1.31.3
export SMTP_URL=smtp://127.0.0.1:1033
export MAILPIT_URL=http://127.0.0.1:8033
export MAIL_FROM='myGame <no-reply@mygame.local>'
export WEB_URL=http://localhost:3233
```

`composeServer` refuses to compose without `SMTP_URL` (an `smtp:` or `smtps:` URL), `MAIL_FROM` or `WEB_URL` (an `http:` or `https:` URL, the web origin the mail links start from). `MAILPIT_URL` is read only by the `SmtpMailer` contract run, which reads the delivered mail back through Mailpit's HTTP API (`GET /api/v1/messages`, `GET /api/v1/message/<ID>`, `DELETE /api/v1/messages`). `pnpm gate` reads only `SMTP_URL` and `MAILPIT_URL` from the shell; the tests take `MAIL_FROM` and `WEB_URL` from `mailEnvironment` in `src/composeServer.testSupport.ts`. `dev` and `start` need `SMTP_URL`, `MAIL_FROM` and `WEB_URL`. CI runs the same image as a second service container of the `gate` job.

## Layout

- `src/app.ts` exports `createApp(dependencies)`, the Hono app with every route. Tests build it with `createApp({ ...server, clock, mailer, failureSink })` over a composed server, swapping the clock, the mailer and the failure sink, and call `app.request(...)`; no socket.
- `src/composeServer.ts` is the composition root: the only module that constructs an adapter and wires it to a port. It refuses to compose without `DATABASE_URL`; it reads no port. It reads `SESSION_COOKIE_SECURE`: unset or `true` marks the session cookie `Secure`, `false` drops the flag for a plain-http dev host, and any other value refuses to compose. It exposes the app's dependencies (`ComposedServer`: `lessons`, `townCatalog`, `memoryTerms`, `clock`, `ids`, `random`, `placedOutBands`, `accounts`, `reportClosings`, `passwords`, `sessionTokens`, `isSessionCookieSecure`, `failureSink`, `mailer`, `webUrl`), `towns`, a lock-free `DrizzleTownRepository` typed as the read-only `TownReader` (`src/town/TownReader.ts`, the port without `save`, so a write that skips the row lock does not compile), `townNews`, a lock-free `DrizzleTownNews` typed as `TownNewsReader`, `cards`, a `DrizzleCardRepository` typed as `CardReader`, and `inTransaction(work)`, which runs `work` inside one Drizzle transaction with a locking `DrizzleTownRepository` and a `DrizzleTownNews`, a `DrizzleAccounts`, a `DrizzleAccountTokens`, a `DrizzleCardRepository`, a `DrizzlePendingReviewRepository`, a `DrizzleReviewLog`, a `DrizzleLessonSlots`, a `DrizzleEarnedSkills`, a `DrizzleBandStarts` and a `DrizzleRegionMap` bound to it (`TransactionStores` in `src/adapters/postgres/postgresTransaction.ts`: `accounts`, `accountTokens`, `cards`, `pendingReviews`, `reviewLog`, `towns`, `townNews`, `lessonSlots`, `earnedSkills`, `bandStarts`, `regionMap`). It also exposes `regionMap`, a lock-free `DrizzleRegionMap` typed as the domain's `RegionMapReader`, which the map's read uses. `work` returns a `Result`; a refusal rolls the whole transaction back. Every town mutation and every sign-up goes through `inTransaction`.
- `src/composeServer.ts` also exposes `mailer`, an `SmtpMailer` typed as `Mailer`, and `webUrl`. It is the only module that constructs a mailer, and it passes `mailer` and `webUrl` to `createApp`; sign-up and the verification resend send the verification mail. `src/auth/Mailer.ts` is the port: `send(mail)` takes a `Mail` (`to`, `subject`, `text`) and answers a `MailDelivery`, `sent` or `failed`. `src/adapters/smtp/SmtpMailer.ts` sends over `nodemailer` from `MAIL_FROM` through a plain `SMTPTransport`, never the pool, so the api keeps no idle socket or timer (N2), with a 3 s connection, 2 s greeting and 3 s socket timeout, so a server that accepts and stays silent cannot hold a request for nodemailer's default minutes, and answers `failed` instead of throwing when the server refuses or cannot be reached. `src/adapters/memory/MemoryMailer.ts` keeps what it sent and `MemoryMailer.failing()` answers `failed`; `src/adapters/mailerContract.ts` is the suite both run. `src/composeServer.testSupport.ts` holds the mail variables every test that composes a server spreads in.
- `src/index.ts` is the production entry (ADR 031): it composes the server from `process.env` and `../content/` and default-exports a plain `Hono` that mounts the server's `fetch`, the one default export of the api, since Vercel loads the module's default. The plain `Hono` keeps a value import of `hono` in the bundle: Vercel's detection needs one, and since every router became an `OpenAPIHono` (#581) the entry is the only file that holds it; without it `vercel build` fails with `No entrypoint found which imports hono`. `apps/api/vercel.json` points its `outputDirectory` at `dist`, where `dist/index.js` is the only candidate, because a TypeScript entry would run Vercel's own type check, which fails under TypeScript 7.
- `src/listen.ts` is the local listener `dev` runs: it reads `API_PORT` through `listenPortOf` (`src/listenPortOf.ts`, an integer from 1 to 65535, else it throws), hands the composed server's `fetch` to `@hono/node-server`, and on `SIGTERM` or `SIGINT` closes the listener, then the server (the pg pool), then exits 0. No test spawns it.
- `src/adapters/postgres/schema.ts` holds the Drizzle tables: `players` (since migration 0010 with the nullable `email_verified_at`, null until the email is verified, with no backfill, so every player stored before it is unverified), `sessions`, `account_tokens` (since migration 0010: `token_digest` primary key under the check `account_tokens_token_digest_hex`, which refuses anything but 64 lowercase hex digits, `player_id` cascading on the player's deletion, `kind` over the enum `account_token_kind` (`reset`, `verify`), `expires_at`, nullable `used_at`); the town tables, `towns`, `town_buildings`, `town_waiting_work`, `town_lesson_slots`, `town_events`, `town_hires`, `town_hiring_orders` and `town_jobs`, and the learning tables, `cards`, `pending_reviews`, `review_log`, `earned_skills`, `band_starts` and `held_out_words`, are described with the migration that created them, below. No rate, capacity or people count is stored (ADR 005, ADR 007).
- `src/adapters/system/` holds `SystemClock`, the only file that calls `Date.now()`, `CryptoIdGenerator`, which issues uuids, `CryptoRandomSource`, the holdout's `RandomSource` over `node:crypto`, `NoPlacedOutBands`, which answers no band until #743 stores placement, `CryptoSessionTokens`, which issues 256-bit base64url session tokens, and `Argon2Passwords`, which hashes with Argon2id at explicit cost (19456 KiB, 2 passes, 1 lane; a test asserts the encoded parameters, since the library's `Algorithm` is an ambient const enum that `verbatimModuleSyntax` refuses, so the algorithm itself is the library default and pinned by that test) and verifies an unknown email against a decoy hash so both refusals cost the same.
- `src/adapters/postgres/DrizzleAccounts.ts` implements `Accounts` (`src/auth/Accounts.ts`) over players and sessions. The api has ports of its own where the domain has no use for one: `Accounts`, since auth is not a domain concern, so its persistence port lives beside the auth flows that depend on it; `AccountTokens` (`src/auth/AccountTokens.ts`) beside it for the same reason; `Mailer` (`src/auth/Mailer.ts`), since no use case of the domain sends a mail; and the read-side ports `TownReader`, `TownNewsReader` and `ReportClosings` (`src/town/`) and `CardReader` and `LessonLibrary` (`src/learning/`), since no rule of the domain reads the news, the Report's close or the content's themes. The session token is never stored: `sessions.token_digest` holds `tokenDigest(token)` (`src/auth/tokenDigest.ts`, the lowercase hex SHA-256 of its UTF-8 bytes), and `openSession`, `renewSession` and `closeSession` digest the token before they touch the row, so a leak of that table is disclosure, not impersonation. The cookie still carries the plain token. The check `sessions_token_digest_hex` refuses anything but 64 lowercase hex digits. A plain SHA-256 suffices, with no salt or slow hash, because the token is 256 random bits.
- `src/adapters/postgres/DrizzleAccountTokens.ts` implements `AccountTokens` over `account_tokens`, storing `tokenDigest(token)`, never the plain token. `issue(token, now)` deletes the player's tokens of that kind and each of the player's used or expired tokens, then inserts, so pruning happens on the next issue for the same player and nothing prunes on a timer. `redeem(token, kind, now)` is one `UPDATE ... SET used_at = now WHERE` digest, kind, `used_at IS NULL` and `expires_at > now` `RETURNING player_id`, so two redeems of one token answer one player. `src/auth/accountTokenExpiryFrom.ts` gives a `reset` token 1 hour and a `verify` token 24 hours. `src/adapters/memory/MemoryAccountTokens.ts` is the in-memory one; `src/adapters/accountTokensContract.ts` is the suite both run. Sign-up and the verification resend issue `verify` tokens. `issue` runs in its own transaction (a savepoint inside `inTransaction`) and first locks the player's row with `SELECT ... FOR NO KEY UPDATE`, so two racing issues serialize without blocking the `FOR KEY SHARE` of a session insert, and leave one live token of a kind; the contract suite's `issueTogether` fixture holds the first transaction open until the second issue waits on that lock. `redeem` also locks the player with `FOR NO KEY UPDATE` inside a savepoint: it reads the live token to find the player, locks the player, then marks the token used, so `issue` and the redeems lock in the same order (player, then tokens) and a redeem racing an issue cannot deadlock.
- `src/auth/` also holds `issueAccountToken(kind, playerId, deps)` (a `CryptoSessionTokens` token with the kind's expiry, issued through the transaction's `accountTokens`), `sendVerificationMail` (link `<WEB_URL>/verify-email?token=<token>`, copy from `@mygame/catalog`, `mailVerificationSubject` and `mailVerificationText`), `verifyEmail` and `resendVerificationMail`. Sign-up issues the verify token inside its transaction and sends the mail after commit, ignoring a failed send. The mail copy lives in `packages/catalog/es.json` under `mail.`, and the api holds no Spanish: refusals carry no prose (ADR 038). `Accounts.StoredPlayer` carries `emailVerified`, read as `email_verified_at IS NOT NULL`; `markEmailVerified(playerId, now)` sets `email_verified_at`. `requestPasswordReset` reads `credentialsOf(email)` in a transaction and issues a `reset` token only for a verified player, then sends `mailResetSubject` and `mailResetText` with `<WEB_URL>/reset-password?token=<token>` after commit and ignores a failed send. `resetPassword` hashes before `inTransaction`, then redeems the `reset` token, calls `storePasswordHash` and `closeSessionsOf` in one transaction. `Accounts` gains `storePasswordHash(playerId, hash)` and `closeSessionsOf(playerId)`.
- `src/routes/auth.ts` also serves `POST /auth/verify-email` (no session; 204, 400 `TokenInvalid` for an unknown, expired, used or `reset` token, 400 with an empty body for a malformed one) and `POST /auth/verify-email/resend` behind `requirePlayer` (204; 204 with no mail once verified; 503 `MailNotSent` when the send fails). Sign-up, sign-in and `GET /auth/session` answer `emailVerified`, mapped field by field. `answerRefusal` also maps `TokenInvalid` (400) and `MailNotSent` (503). It also serves `POST /auth/forgot-password` (no session; 202 empty for any well-formed email, 400 empty for a malformed one) and `POST /auth/reset-password` (no session; 204 with no cookie, 400 `TokenInvalid` for an unknown, expired, used or `verify` token, 400 `WeakPassword` for a password under 8 characters before any store call, 400 empty for a body without a token).
- `src/auth/` holds `signUp` and `signIn`. Sign-up hashes the password, then in one `inTransaction` inserts the player, opens the session and issues the verify token; it founds no town, since the player names it on the first signed-in visit (`POST /town`, ADR 040).
- `createApp` returns an `OpenAPIHono` (`@hono/zod-openapi`) and serves `GET /openapi.json`, an OpenAPI 3.0.0 document: 3.0, not 3.1, because openapi-generator's 3.1 support is partial (ADR 034). A route is in the document when its module registers a `createRoute` declaration on its `openAPIRegistry` (`src/routes/authDeclarations.ts`, `src/routes/townDeclarations.ts`) and serves the handler at the declaration's `path`; `route()` carries a child `OpenAPIHono`'s declarations up with the mount prefix, a path parameter written `{param}`, so every module on the path to a declared route is an `OpenAPIHono`. The declarations are registered with `registerPath`, never `app.openapi`, because `app.openapi` validates the body itself and answers 415 or a plain-text 400 where the route answers its own refusal: the handlers keep parsing with the contract schema. Request and response schemas come from `@mygame/contracts`, named through zod's `.meta({ id })` into `components.schemas`; `refusalResponse` (`src/http/refusalResponse.ts`) declares a status that answers `ApiError`. Every route the app serves is declared (#573, #575): each module registers its declarations in a loop and serves each handler with `routes.on(declaration.method, honoPathOf(declaration), …)` (`src/http/responseDeclarations.ts`, which turns `{param}` into `:param`), so the method and the path cannot drift from the document. `src/openApiRoutes.test.ts` fails on a served route missing from the document; `src/openApiConformance.test.ts` runs every operation and checks the answered status is declared and a non-empty body parses with the declared schema. A refusal that answers an empty body (`MalformedRequest`, `SignedOut`) is described in the status's description. `createApp` registers the `sessionBearer` security scheme (http, bearer); every declaration of a route behind `requirePlayer` goes through `signedInRoute` (`src/http/responseDeclarations.ts`), which adds that `security` and the empty 401, so a signed-in route never declares either by hand.
- `src/http/requirePlayer.ts` is the only reader of the session token. It reads the `session` cookie (`src/http/sessionCookie.ts`) and, only when the request carries no session cookie at all, `Authorization: Bearer <token>` (`src/http/bearerToken.ts`); a dead cookie answers 401 even beside a live bearer (#576). It renews the session row to now + 30 days in one `UPDATE ... WHERE expires_at > now RETURNING`, rewrites the cookie only when the token came from the cookie (a bearer request gets no `Set-Cookie`) and yields `playerId` and `sessionToken` in `c.var`; without a live session it answers 401 `SignedOut`, empty body. `src/routes/signedInCarriers.test.ts` drives every route behind it with the cookie, the bearer and neither, and fails when the routes answering an empty 401 differ from the operations the document secures.
- `src/http/answerRefusal.ts` is the one module that maps a `Refusal` (every `DomainError` kind plus the api's `EmailTaken`, `InvalidCredentials`, `WeakPassword`, `MalformedEmail`, `MalformedRequest`, `SignedOut`) to a status and, for the kinds `ApiErrorSchema` knows, a body of the kind alone or, for the kinds with fields (the town's `WaitingListFull`, `NotEnoughPeople`, `NotEnoughResources`, `TopLevelReached` and `BuildingWorkNotFound`, the office's `OfficeTooLow`, `HiringSlotBusy` and `HiringOrderNotFound`, the job's `JobHoursOutOfRange` and `NotEnoughHiresAtHome`, and the school's `LearningCapReached`), the kind and its typed `params` copied from the refusal (`{ "kind": "WaitingListFull", "params": { "cap": 4 } }`), never a line of copy (ADR 038, #736); each client renders the line from its own copy. The map's and the job's kinds (#782): `AreaNotFound` 404, `InvalidTeam` and `JobSiteOutOfBounds` 400 and `JobHoursOutOfRange` 400 with `{ hours, maxHours }`, `TeamAlreadyOut`, `JobToOwnSite`, `SiteHeld`, `JobNotFound` and `JobAlreadyReturning` 409 and `NotEnoughHiresAtHome` 409 with `{ hire, count, atHome }`. A kind the wire does not name answers its status with an empty body, as the stored-job refusals `InvalidJobHours` and `InvalidPayPercent` 500 do. It records the refusal's `kind` in `c.var.refusalKind` (declared on Hono's `ContextVariableMap` in that file) for the failure report.
- `src/http/reportServerFailures.ts` is the failure report (#685): `createApp` mounts it before every route, so it runs once at the boundary, never per route, and it writes exactly one line to `failureSink`, a `FailureSink` (`src/http/FailureSink.ts`, `write(line)`), for every answer with a status of 500 or above, and nothing for any status under 500. A line is `<method> <path> <status>`, then the refusal's `kind` (`GET /town 500 UnknownTownBuildingLevel`, `POST /auth/verify-email/resend 503 MailNotSent`) or, for a thrown error, its class (`error.constructor.name`, since `DrizzleQueryError` leaves `name` as `Error`) and, when its `cause` carries a string `code`, that code (`POST /auth/sign-up 500 DrizzleQueryError 23514`, `POST /auth/sign-in 500 TypeError`). A thrown error's `message` is never written: drizzle-orm's `DrizzleQueryError` message is `Failed query: <query>\nparams: <params>`, so it would carry an email and a password hash. The path is `c.req.path`, without the query; a line never carries a header, a cookie, a bearer token, the body, a password or an email, nor any field of the refusal beyond its `kind`. `createApp`'s `onError` answers a thrown error with an empty 500, and Hono's `c.error` carries it to the report. `composeServer` binds the sink to the process's standard error through `console.error`, the api's one `noConsole` exception, with its `biome-ignore` reason; tests pass a sink that collects lines (`src/http/reportServerFailures.test.ts`), never a spy on `console`. A stock stored above its capacity is not a failure: the read answers 200 with the stock frozen (ADR 005, amendment), so it writes nothing.
- `src/routes/auth.ts` serves `POST /auth/sign-up` (201 `Player`), `POST /auth/sign-in` (200 `Player`), `POST /auth/sign-in/native` (200 `NativeSession`, `{ token, player }`, no cookie; the Android client's sign-in, refusing as `/auth/sign-in` does), `POST /auth/sign-up/native` (201 `NativeSession`, no cookie; the Android client's sign-up, refusing as `/auth/sign-up` does and sending the same verification mail), `POST /auth/sign-out` (204) and `GET /auth/session` (200 `Player`). Only the two native routes answer the token in a body; `Player` never carries it. The cookie is `session`, `HttpOnly; Secure; SameSite=Lax; Path=/`, 30 days; `Secure` follows `SESSION_COOKIE_SECURE`.
- `src/adapters/json/JsonTownCatalog.ts` (#759) implements the domain's `TownCatalog` from `content/town/`: one JSON per building (`homes.json`, `farm.json`, `factory.json`, `powerStation.json`, `storage.json`, `school.json`, `office.json`, ten levels each), parsed by `@mygame/contracts`'s `BuildingContentSchema`, and `town.json`, the settings, parsed by `TownContentSchema`, its `seasons.epoch` handed to the domain as an `Instant`. It fails at start-up on a malformed file or one that describes another building. `composeServer` builds it from `content/town/` and exposes it as `townCatalog`.
- `src/adapters/postgres/DrizzleTownRepository.ts` (#759) implements `TownRepository` over `towns`, `town_buildings`, `town_waiting_work`, `town_hires`, `town_hiring_orders` (#777) and `town_jobs` (#781): `townOf(playerId)` is one query, the town row with its level rows, its waiting work, its hire counts, its hiring order and its job each a `json_agg` subquery (`jsonAggregateOf`, the waiting work ordered by `position`), never a join, so the race probe's unprefixed `select "id", "player_id", "region", %` still matches; it throws on a town missing the count of either hire; built with `'lockedForUpdate'` it takes `FOR UPDATE OF towns`, with `'lockFree'` no lock. It reads the work slot from the eight nullable `work_*` columns and throws on a half-written one, and the player's `earned_skills` as a `json_agg` subquery ordered by `byEarnedAt` (#769); `save` never writes a skill. `townWithSchoolOf(playerId)`, on the `TownReader` only, answers the town, its `town_lesson_slots` row (left-joined), the player's cards (`aggregatedCards.ts`) and held-out words (`aggregatedHeldOutWords.ts`) in the same one statement, so `GET /town` stays one round trip. `save` upserts the town row, the slot columns, the seven level rows and both hire counts, replaces the waiting work (delete, then insert at positions 0..n−1), upserts the hiring order when busy or deletes it when idle and upserts the job when out or deletes it when idle in one transaction (a savepoint inside `inTransaction`) and maps `towns_site_unique` to `SiteTaken` and `towns_player_unique` to `PlayerAlreadyHoldsTown`. `src/adapters/memory/MemoryTownRepository.ts` is the in-memory one; `src/adapters/townRepositoryContract.ts` is the suite both run, a race of two saves on one site included. The town enum `town_building` spells `power_station`; the adapter maps it.
- Town News (#764, ADR 040): `src/town/TownNewsReader.ts` is the api-side read port (`newsOf(townId)`, newest `occurred_at` first, a tie newest `id` first; `newsAfter(townId, after)`, the same order, strictly after `after`), beside the domain's `TownNews` writer. `src/adapters/postgres/DrizzleTownNews.ts` implements both over `town_events`; `payloadOf` and `eventOf` switch exhaustively over the kinds and alone tie a kind to its columns (`buildingWorkStopped` and `hiringStopped` refund, `jobBack` and `jobCalledBack` pay and `cleanUpDone` reward in the four `amount_*`; `hiringStopped` delivered in `count` and stopped in `stopped_count`; the job and clean-up kinds' site in `region`, `area` and `site`). `record` inserts, then deletes the town's rows beyond the latest `keptEventsPerTown` = 100 (`src/town/TownNewsReader.ts`) on the same session, as ADR 013 asks; with no events it does nothing. `src/adapters/memory/MemoryTownNews.ts` is the in-memory one; `src/adapters/townNewsContract.ts` is the suite both run, a rollback of the transaction that wrote an event included. `inTransaction` hands `towns` (a locking `DrizzleTownRepository`) and `townNews` in `TransactionStores`; the town routes (`routes/town.ts`, below) write through them. ## Gotchas

- Routes stay thin: parse with the contract schema, call the use case, map the `Result`. No rule lives in a route.
- Adapters implement ports defined in `@mygame/domain`; the api-side exceptions are `Accounts`, `AccountTokens` and `Mailer` in `src/auth/`, since auth stays out of the domain, and the read-side ports `TownReader`, `TownNewsReader` and `ReportClosings` (`src/town/`) and `CardReader` and `LessonLibrary` (`src/learning/`).
- No `nodemailer` import outside `src/adapters/smtp/`. nodemailer 10 ships its own types, so no `@types/nodemailer`.
- Point `SMTP_URL` at `127.0.0.1`, not `localhost`: nodemailer resolves a host name through `dns.resolve4` before it falls back to `dns.lookup`, and on macOS that query for `localhost` can stall the first send for about 5 s, past Vitest's timeout.
- Mailpit's `Text` ends with the line break that closes the SMTP body; the contract run strips one trailing `\r\n` before comparing.
- A write through a store not bound to the `inTransaction` transaction that touches a row referencing `towns` blocks on the town's `FOR UPDATE` lock (the foreign key takes `FOR KEY SHARE`); every store inside `work` must come from `TransactionStores`.
- No Drizzle import outside an adapter.
- Every town mutation runs through `mutateTown` in one transaction that first locks the player's row, then the town row with `SELECT ... FOR UPDATE`, then applies and writes (N4, ADR 006). Two concurrent mutations serialize on those locks.
- The migration test applies every migration inside one transaction after dropping `public` and `drizzle`, and rolls back, so it sees an empty database and leaves the session's database as it found it.
- Stop the dev api before `pnpm gate`: dev and the gate share the session's one database, so a request racing the migration test's `DROP SCHEMA public CASCADE` can fail that test with `deadlock detected`, and the rows the dev api writes can make other tests read the wrong data (#583).
- Drizzle's `insert` lists every column of the current `schema.ts` and sends `default` for any that is missing, so `db.insert(towns)` fails on a database at an older migration. A migration test seeds the previous version's rows with `client.query` and plain SQL.
- `vitest.globalSetup.ts` applies `migrations/` to `DATABASE_URL` before the suite, so a fresh database (CI's service container) has the tables. The api test files share that database and truncate it, so `vitest.config.ts` sets `fileParallelism: false`.
- The race tests in `composeServer.test.ts` (`queues the second of two concurrent starts on one town behind the first`, `debits both costs when two starts on one town race`) pause the first transaction after its read and resume once the second waits on a lock in `pg_stat_activity`; the probe matches the start of the query, not its `for update` tail, because `pg_stat_activity.query` keeps only `track_activity_query_size` bytes (1 kB by default). The probe is bounded. With the lock removed the tests fail every time.
- A table that references `players` or `towns` joins every `TRUNCATE` list in the api tests that truncates the table it references.
- The content copies in `composeServer.test.ts` must include `lessons/` and `town/`: they use `cpSync` recursive, and start-up reads `lessons/curriculum.json`, `lessons/words.json`, every lesson file the curriculum lists and `lessons/ngsl-1.2.csv`, and the town's content under `town/`.
- Drizzle runs every pending migration of one `db:migrate` in one transaction, and Postgres refuses to use a value that `ALTER TYPE ... ADD VALUE` added in the same transaction unless the type was created there too; a migration must never use a value that it, or an earlier migration of the same run, adds.
- `db:generate` needs `DATABASE_URL` set, because `drizzle.config.ts` refuses to load without it, even though generate never connects.
- A password shorter than 8 characters fails `SignUpRequestSchema` and `ResetPasswordRequestSchema`. The sign-up routes and the reset route map a parse failure through `requestRefusalOf` (#604; `src/http/requestRefusalOf.ts`): an `invalid_format` issue on `email` to `MalformedEmail`, a `too_small` issue on `password` to `WeakPassword`, a `too_small` issue on the town's `name` to `BlankTownName`, the first of those in that order when several apply, and any other issue to `MalformedRequest`; an email that is not text is `MalformedRequest`, empty body.
- `pnpm add` in pnpm 11 ignores `save-exact` from `.npmrc` and writes a caret; fix the specifier by hand. `@node-rs/argon2` ships prebuilt binaries, so it needs no `allowBuilds` entry.
- No pepper or secret is configured: Argon2id salts each hash itself, so no auth env variable exists yet.
- `players_email_unique` is a unique index on `lower(email)`: the email is stored as typed and compared case-insensitively.
- `drizzle-kit generate` asks whether a new column renames an old one, and that prompt needs a TTY; a shell without one fails with "Interactive prompts require a TTY terminal". Run `db:generate --custom --name <change>` instead: it writes an empty SQL file, the journal entry and a snapshot copied unchanged from the previous one. Write the SQL by hand, edit the snapshot to match `schema.ts`, and confirm with `db:generate --name probe`, which must report no schema change and write no file.
- `drizzle-orm`, `pg` and `drizzle-kit` have one consumer, so their versions live here, not in the catalog.
- Import `@mygame/contracts` and `@mygame/domain` only from their root entries; `rg -n "from '@mygame/(domain|contracts)/src" apps packages` stays empty.
- The workspace packages export raw `.ts` with extensionless relative imports, which plain `node` cannot load (`ERR_MODULE_NOT_FOUND`). Production runs the esbuild bundle, which inlines them; `dev` runs through `tsx`, which resolves them at runtime. `index.ts` and `listen.ts` find `../content/` from `import.meta.url`, and `dist/` sits beside `src/`, so the bundle resolves the same directory and Vercel's trace copies `content/` into the function.
- `hono`, `@hono/zod-openapi`, `@hono/node-server` and `esbuild` have one consumer, so their versions live here, not in the catalog; `typescript`, `vitest`, `tsx` and `@types/node` come from `catalog:`.
- `esbuild` (a devDependency here, and under `tsx`) is listed in `allowBuilds` in `pnpm-workspace.yaml`; pnpm 11 fails the install on an unreviewed build script.
- `@node-rs/argon2` loads a prebuilt binary per platform, and a function takes the architecture of the machine that ran `vercel build`: only the CI build on Linux x64 ships the binary the function loads, so never deploy a `vercel build` run on macOS.
