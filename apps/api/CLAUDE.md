# apps/api

Hono on Node: the HTTP adapters, the persistence adapters that implement the domain ports, auth, and the composition root.

## Commands

- `API_PORT=3106 pnpm --filter @mygame/api dev` — `tsx watch src/server.ts`. Use the port the dispatch assigns, never a default. Add `SESSION_COOKIE_SECURE=false` when a browser reaches the api over plain `http://localhost`: Safari refuses a `Secure` cookie there.
- `pnpm --filter @mygame/api build` — esbuild bundles `src/server.ts` into one ESM file, `dist/server.js`: the workspace packages and `zod` are inlined, `hono`, `@hono/node-server`, `pg`, `drizzle-orm`, `@node-rs/argon2` and `nodemailer` stay external imports. A new runtime dependency gets its own `--external:` in the script.
- `API_PORT=3106 DATABASE_URL=... SMTP_URL=... MAIL_FROM=... WEB_URL=... pnpm --filter @mygame/api start` — `node dist/server.js`, the production entry. `/health` answers without a reachable database. CI builds and probes it after the gate.
- `pnpm --filter @mygame/api test` — Vitest, `src/**/*.test.ts`. Route tests compose the real server on the session's Postgres, with the real adapters; an in-memory adapter exists only to run a port's contract suite beside the Drizzle one.
- `pnpm --filter @mygame/api typecheck` — `tsc --noEmit` over `src`, the Vitest config and `drizzle.config.ts`.
- `pnpm --filter @mygame/api db:generate --name <change>` — `drizzle-kit generate`: diffs `src/adapters/postgres/schema.ts` against `migrations/meta` and writes the next SQL migration. Commit the SQL and the `meta` files together.
- `pnpm --filter @mygame/api db:migrate` — `drizzle-kit migrate`: applies pending migrations to `DATABASE_URL`.
- `docker build -f apps/api/Dockerfile --target api -t mygame-api .` from the repo root — the production image: `node dist/server.js` as the `node` user (uid 1000) in `/repo/apps/api`, beside `content/` and the production dependencies only. It reads the same variables as `start`; nothing secret is baked in. Its `HEALTHCHECK` runs `fetch` from `node -e` against `127.0.0.1:$API_PORT/health`, since the slim image has no `curl`.
- `docker build -f apps/api/Dockerfile --target migrate -t mygame-migrate .` from the repo root — the one-shot migrate image: `drizzle-kit migrate` over `migrations/` with `drizzle.config.ts`, as the `node` user. `docker run --rm -e DATABASE_URL=... mygame-migrate` exits 0 when every migration is applied, a second run included, and 1 when the database is unreachable.
- `pnpm gate` from the repo root before every commit.

## Local database

Postgres 18 in Docker, one container and one host port per session, never a system service and never the owner's database. The container is named `mygame-<session>-pg`, the database `mygame_<session>`, and the dispatch assigns the port:

```
docker run -d --name mygame-schema-pg -e POSTGRES_PASSWORD=mygame -e POSTGRES_DB=mygame_schema -p 5433:5432 postgres:18
export DATABASE_URL=postgres://postgres:mygame@localhost:5433/mygame_schema
```

`DATABASE_URL` must be set in the shell that runs `pnpm gate`; the migration test fails without it. CI runs the same image as a service container of the `gate` job.

## Local mail

Mailpit in Docker beside the Postgres one, one container and two host ports per session, the ports assigned by the dispatch. The container is named `mygame-<session>-mail`; the tag is the one `.github/workflows/ci.yml` pins, never `latest`:

```
docker run -d --name mygame-schema-mail -p 1033:1025 -p 8033:8025 axllent/mailpit:v1.31.3
export SMTP_URL=smtp://127.0.0.1:1033
export MAILPIT_URL=http://127.0.0.1:8033
export MAIL_FROM='myGame <no-reply@mygame.local>'
export WEB_URL=http://localhost:3233
```

`composeServer` refuses to compose without `SMTP_URL` (an `smtp:` or `smtps:` URL), `MAIL_FROM` or `WEB_URL` (an `http:` or `https:` URL, the web origin the mail links start from). `MAILPIT_URL` is read only by the `SmtpMailer` contract run, which reads the delivered mail back through Mailpit's HTTP API (`GET /api/v1/messages`, `GET /api/v1/message/<ID>`, `DELETE /api/v1/messages`). `pnpm gate` reads only `SMTP_URL` and `MAILPIT_URL` from the shell; the tests take `MAIL_FROM` and `WEB_URL` from `mailEnvironment` in `src/composeServer.testSupport.ts`. `dev` and `start` need `SMTP_URL`, `MAIL_FROM` and `WEB_URL`. CI runs the same image as a second service container of the `gate` job.

## Layout

- `src/app.ts` exports `createApp(dependencies)`, the Hono app with every route. Tests build it with `createApp({ ...server, clock, mailer })` over a composed server, swapping the clock and the mailer, and call `app.request(...)`; no socket.
- `src/composeServer.ts` is the composition root: the only module that constructs an adapter and wires it to a port. It reads `API_PORT` and refuses to compose unless it is an integer from 1 to 65535, and refuses to compose without `DATABASE_URL`. It reads `SESSION_COOKIE_SECURE`: unset or `true` marks the session cookie `Secure`, `false` drops the flag for a plain-http dev host, and any other value refuses to compose. It exposes the app's dependencies, `fiefs`, a lock-free `DrizzleFiefRepository` typed as the read-only `FiefReader` (`src/fief/FiefReader.ts`, the port without `save`, so a write that skips the row lock does not compile), and `inTransaction(work)`, which runs `work` inside one Drizzle transaction with a locking `DrizzleFiefRepository`, a `DrizzleChronicle`, a `DrizzleAccounts`, a `DrizzleAccountTokens` and a `DrizzleCampRegistry` bound to it (`TransactionStores`: `fiefs`, `chronicle`, `accounts`, `accountTokens`, `camps`). `work` returns a `Result`; a refusal rolls the whole transaction back. Every fief mutation and every sign-up goes through `inTransaction`.
- `src/composeServer.ts` also exposes `chronicle`, a lock-free `DrizzleChronicle` typed as `ChronicleReader`.
- `src/composeServer.ts` also exposes `mailer`, an `SmtpMailer` typed as `Mailer`, and `webUrl`. It is the only module that constructs a mailer, and it passes `mailer` and `webUrl` to `createApp`; sign-up and the verification resend send the verification mail. `src/auth/Mailer.ts` is the port: `send(mail)` takes a `Mail` (`to`, `subject`, `text`) and answers a `MailDelivery`, `sent` or `failed`. `src/adapters/smtp/SmtpMailer.ts` sends over `nodemailer` from `MAIL_FROM` through a plain `SMTPTransport`, never the pool, so the api keeps no idle socket or timer (N2), with a 3 s connection, 2 s greeting and 3 s socket timeout, so a server that accepts and stays silent cannot hold a request for nodemailer's default minutes, and answers `failed` instead of throwing when the server refuses or cannot be reached. `src/adapters/memory/MemoryMailer.ts` keeps what it sent and `MemoryMailer.failing()` answers `failed`; `src/adapters/mailerContract.ts` is the suite both run. `src/composeServer.testSupport.ts` holds the mail variables every test that composes a server spreads in.
- `src/server.ts` is the listener: it hands the composed server to `@hono/node-server`, and on `SIGTERM` or `SIGINT` closes the listener, then the server (the pg pool), then exits 0, so `docker stop` ends the api without waiting out the grace period and its exit 137. No test spawns it: the behavior is a process signal on a listening socket, and a test would need a fixed port and polling `/health` for readiness; the image check in #446 proves it.

- `src/adapters/postgres/DrizzleFiefRepository.ts` implements `FiefRepository`. `fiefsOf(playerId)` answers the ids of the fiefs a player holds, ordered by province then plot, in one lock-free query. `fiefOf(fiefId)` reads by the fief's id, never the player's, and is one query: the fief row left-joined to its level rows, its queue entries, its art rows, its unit rows, its recruit order and its march. The joins multiply the rows (levels × entries × arts × units; the order and the march are at most one row each), so the mapper deduplicates levels by building, entries by position, arts by art and units by kind, then orders the entries by position; the order and the march come from the first row. With `'lockedForUpdate'` it takes `FOR UPDATE OF fiefs` on the row of that id, so the lock is the fief's, not the player's; with `'lockFree'` it takes no lock, so a read never queues behind a mutation. `save` runs one transaction, a savepoint inside `inTransaction`: it upserts the fief row, its built level rows, its studied art rows and its unit rows with a count above 0, deletes the unit row of every kind whose count is 0, so a count that drops to 0 reads back as 0, replaces its queue entries (delete, then insert at positions 0..n−1), replaces its recruit order (delete, then insert when one is open) and replaces its march (delete, then insert when a march is away, with `recalled_at` null unless the march holds `recalledAt`; a forage march with `march_order` `forage`, no camp and `fought` false, an attack with `march_order` `attack`, its `camp` in `camp_tier` and `camp_strength` and its `fought`). It restores a `march_order` `attack` row as an attack march and throws on one whose camp columns are null or whose tier is outside 1..3, as it does on a half-written slot. A building without a row is unbuilt; an art without a row is at level 0; a unit kind without a row counts 0. A march row holds the party's `units` in `infantry_count`, `cavalry_count`, `archer_count` and `settler_count`, one column per kind, so the march stays one row and the fief read stays one query.
- `src/adapters/postgres/DrizzleChronicle.ts` implements `ChronicleWriter` and `ChronicleReader` (`src/fief/ChronicleReader.ts`, `eventsOf(fiefId)`, newest `occurred_at` first, a tie newest `id` first, at most `keptEventsPerFief` = 100). `rowOf` and `eventOf` switch exhaustively over the event kinds, and they alone tie a kind to its columns (`recruitsCancelled` to `unit`, `count` as `delivered`, `cancelled_count` as `cancelled` and `refund_*`; `marchReturned` to `infantry_count`, `cavalry_count`, `archer_count` and `settler_count` as `units`, `province`, `plot`, `recalled` and `refund_*` as `loot`; `battleFought` to `infantry_count`, `cavalry_count`, `archer_count` and `settler_count` as `unitsLost`, `province`, `plot`, `camp_tier` as `tier`, `camp_lost` as `campLost` and `won`; `foundingSent` and `fiefFounded` to `province`, `plot` and `fief_name` as `name`; `transportSent` and `transportArrived` to `province`, `plot`, `fief_name` as `name` and `refund_*` as `cargo`). `record` inserts, then deletes the fief's rows beyond the latest 100 on the same session; with no events it does nothing. `src/adapters/memory/MemoryChronicle.ts` is the in-memory one; `src/adapters/chronicleContract.ts` is the suite both run. The chronicle is never joined into the fief read. `src/adapters/postgres/storedKinds.ts` holds the building, art and unit enum maps both postgres adapters share; `src/adapters/postgres/isCampTier.ts` narrows a stored tier to `CampTier` for both.
- `src/adapters/json/JsonBuildingCatalog.ts` implements `BuildingCatalog` from `content/`: one JSON per building (seven, `library.json` and `barracks.json` included; the barracks at levels 1 to 10 from 200 wood, 120 stone, 60 iron, 360 s and 1 peasant, with no effect), `fief.json` for the settings (its `seasons` holds the `epoch` ISO instant, which the adapter hands to the domain as an `Instant`, `daysPerSeason`, `multiplierPercent`, a whole percent from 1 per season and resource, and `durationPercent`, a strict `{ build, study, train, road }` of whole percents from 1 per season; the shipped content has `summer.build` 75, `winter.study` 75, `spring.train` 75, `autumn.road` 75 and every other cell 100, and the dispatch of a march or an attack reads `road` (ADR 022); its `units` carries, per `UnitKind`, a `cost`, a `durationSeconds`, a `peasantOccupancy`, a `strength`, a `carry`, a `roadPercent` and a `barracksLevel`, whole counts, `strength` and `carry` from 0 and the rest from 1, so a missing field, a negative strength or carry or any other 0 fails at start-up: infantry at 20 wood, 10 iron, 30 food, 90 s, 1 peasant, strength 1, carry 48, road percent 100, barracks level 1; cavalry at 30 wood, 40 iron, 20 gold, 80 food, 300 s, 2 peasants, strength 2, carry 120, road percent 50, barracks level 3; archer at 40 wood, 10 iron, 5 gold, 40 food, 150 s, 1 peasant, strength 1, carry 24, road percent 100, barracks level 2; settler at 1000 wood, 1000 stone, 600 iron, 100 gold, 1000 food, 7200 s, 4 peasants, strength 0, carry 0, road percent 100, barracks level 5), and `content/arts/smithing.json` and `content/arts/masonry.json` parsed with `ArtContentSchema`. Beside the port it exposes `digestTerms()`, the content's `digest` (`absenceSeconds` 3600 in the shipped content), which `composeServer` hands to the app as `digestTerms`; the domain never reads it. It fails at start-up on a malformed file or on an art file that names the other art.
- `fief.json`'s `forage` carries 600 s per province, 60 s per plot, a longest stay of 8 h and `yieldPerHour` per terrain (3 on lowlands food and wood, uplands wood and stone, ridges stone and iron, gold always 0); `FiefContentSchema` refuses a gold rate above 0 and the api does not start.
- `fief.json`'s `camps` carries `campFraction` 0.2 (a number from 0 to 1), `lootPerStrength` 60 and `tiers` keyed `1`, `2` and `3`, each a `{ maxStrength, regrowHours }` of whole counts from 1: 6 in 6 h, 15 in 12 h and 40 in 24 h. A missing tier or field, or a fraction above 1, fails the parse and the api does not start. The adapter's `...fief` spread hands it to the domain as `FiefSettings.camps`. Changing `campFraction` moves every camp, a content edit, as `plotsPerProvince` does (ADR 014).
- `src/adapters/memory/MemoryFiefRepository.ts` is the in-memory `FiefRepository`. `src/adapters/fiefRepositoryContract.ts` is the port's contract suite, and both adapters' tests run it.
- `src/adapters/postgres/DrizzleCampRegistry.ts` implements the domain's `CampRegistry` over `camp_battles`, one query per method on the session it is built with: `lastBattleOf` the plot's row with the latest `fought_at`, a tie read by the highest `id`, the latest insert; `lastBattlesIn` one such row per plot of a kingdom's province through `DISTINCT ON (plot)`, ordered by plot; `record` inserts. `src/adapters/memory/MemoryCampRegistry.ts` is the in-memory one; `src/adapters/campRegistryContract.ts` is the suite both run. `postgresTransaction` builds one on the transaction as `TransactionStores.camps`, which `mutateAfterResolve` hands both the resolve and the mutation (`FiefStores`), so a battle row commits or rolls back with the fief that fought it; the dry run of `currentFiefOf` passes `discardingCamps`, as it passes `discardingChronicle`. `composeServer` also builds one on the pool, outside any transaction, exposed as `camps`, a `CampReader` (`src/kingdom/CampReader.ts`, the port without `record`, so a battle written outside a transaction does not compile); only the map routes read it.
- `src/adapters/postgres/DrizzleKingdomMapReader.ts` implements `KingdomMapReader` over the address columns of `fiefs`, with one lock-free query per method: `addressOf(fiefId)` by `id`, answering a `HeldAddress` (the `address` and its holder's `playerId`), `lastOccupiedProvince` as `max(province)` of the kingdom (0 when none), `holdersIn` as the fiefs of one kingdom and province ordered by `plot`, and `reservationsIn` as the `fief_marches` rows with a `founding_name` and no `recalled_at` whose `province` is the one asked, joined to the sending fief for its `kingdom` (`fief_marches` holds none) and its `player_id`, ordered by `plot`. `src/adapters/memory/MemoryKingdomMapReader.ts` reads the fiefs a `MemoryFiefRepository` holds through `heldFiefs()`, and the reservations through `reservedPlotOf` (`src/adapters/memory/reservedPlotOf.ts`), which `MemoryFiefRepository` shares. `src/adapters/kingdomMapReaderContract.ts` is the suite both run, seeded through the `FiefRepository` of the same store.
- `src/adapters/system/` holds `SystemClock`, the only file that calls `Date.now()`, `CryptoIdGenerator`, which issues uuids, `CryptoSessionTokens`, which issues 256-bit base64url session tokens, and `Argon2Passwords`, which hashes with Argon2id at explicit cost (19456 KiB, 2 passes, 1 lane; a test asserts the encoded parameters, since the library's `Algorithm` is an ambient const enum that `verbatimModuleSyntax` refuses, so the algorithm itself is the library default and pinned by that test) and verifies an unknown email against a decoy hash so both refusals cost the same.
- `src/adapters/postgres/DrizzleAccounts.ts` implements `Accounts` (`src/auth/Accounts.ts`) over players and sessions. The api has seven ports of its own: `Accounts`, since auth is not a domain concern, so its persistence port lives beside the auth flows that depend on it; `AccountTokens` (`src/auth/AccountTokens.ts`) beside it for the same reason; `ChronicleReader` (`src/fief/`), since the domain never reads the chronicle; `Mailer` (`src/auth/Mailer.ts`), since no use case of the domain sends a mail; and `DigestAcknowledgements`, `GuidanceDismissals` and `SeenHints` (#478), since no rule of the domain reads what the lord acknowledged, dismissed or has seen. The session token is never stored: `sessions.token_digest` holds `tokenDigest(token)` (`src/auth/tokenDigest.ts`, the lowercase hex SHA-256 of its UTF-8 bytes), and `openSession`, `renewSession` and `closeSession` digest the token before they touch the row, so a leak of that table is disclosure, not impersonation. The cookie still carries the plain token. The check `sessions_token_digest_hex` refuses anything but 64 lowercase hex digits. A plain SHA-256 suffices, with no salt or slow hash, because the token is 256 random bits.
- `src/adapters/postgres/DrizzleAccountTokens.ts` implements `AccountTokens` over `account_tokens`, storing `tokenDigest(token)`, never the plain token. `issue(token, now)` deletes the player's tokens of that kind and each of the player's used or expired tokens, then inserts, so pruning happens on the next issue for the same player and nothing prunes on a timer. `redeem(token, kind, now)` is one `UPDATE ... SET used_at = now WHERE` digest, kind, `used_at IS NULL` and `expires_at > now` `RETURNING player_id`, so two redeems of one token answer one player. `src/auth/accountTokenExpiryFrom.ts` gives a `reset` token 1 hour and a `verify` token 24 hours. `src/adapters/memory/MemoryAccountTokens.ts` is the in-memory one; `src/adapters/accountTokensContract.ts` is the suite both run. ## Gotchas

- Routes stay thin: parse with the contract schema, call the use case, map the `Result`. No rule lives in a route.
- Adapters implement ports defined in `@mygame/domain`; the api-side exceptions are `Accounts`, `AccountTokens` and `Mailer` in `src/auth/`, since auth stays out of the domain, `ChronicleReader` in `src/fief/`, since the domain never reads the chronicle, and `DigestAcknowledgements` (`src/digest/`), `GuidanceDismissals` (`src/guidance/`) and `SeenHints` (`src/hint/`), the S22 stores.
- No `nodemailer` import outside `src/adapters/smtp/`. nodemailer 10 ships its own types, so no `@types/nodemailer`.
- Point `SMTP_URL` at `127.0.0.1`, not `localhost`: nodemailer resolves a host name through `dns.resolve4` before it falls back to `dns.lookup`, and on macOS that query for `localhost` can stall the first send for about 5 s, past Vitest's timeout.
- Mailpit's `Text` ends with the line break that closes the SMTP body; the contract run strips one trailing `\r\n` before comparing.
- A write through a store not bound to the `inTransaction` transaction that touches a row referencing `fiefs` blocks on the fief's `FOR UPDATE` lock (the foreign key takes `FOR KEY SHARE`); every store inside `work` must come from `TransactionStores`.
- No Drizzle import outside an adapter.
- Every mutation of a fief runs in one transaction that first locks the fief row with `SELECT ... FOR UPDATE`, then materializes, applies and writes (N4, ADR 006). Two concurrent mutations serialize on that lock.
- The migration test applies every migration inside one transaction after dropping `public` and `drizzle`, and rolls back, so it sees an empty database and leaves the session's database as it found it.
- Drizzle's `insert` lists every column of the current `schema.ts` and sends `default` for any that is missing, so `db.insert(fiefs)` fails on a database at an older migration. A migration test seeds the previous version's rows with `client.query` and plain SQL.
