# GitHub workflows

## The gate

CI runs exactly `pnpm gate`, whose definition is the `gate` script in the root `package.json`. The workflow never lists the gate's steps by hand; when the gate changes, `package.json` changes and CI follows. The one step outside the gate is the api build-and-probe, which needs a built bundle, so it lives in the workflow. Local and CI run the same command on the same Node major (`.node-version`).

## `ci.yml`

- Triggers: `pull_request` on any branch, `push` to `trunk`.
- Steps: the test database step the `gate` job's services line names, checkout, `pnpm/action-setup` (reads `packageManager` from `package.json`, so no version is repeated), `actions/setup-node` with `node-version-file: .node-version` and `cache: pnpm`, `pnpm install --frozen-lockfile`, `pnpm gate`, then the api build-and-probe: `pnpm -r build`, then `node --input-type=module --eval` imports `apps/api/dist/index.js`, the bundle Vercel runs, and asks its default export's `fetch` for `/health`; anything but 200, or a bundle that fails to compose, fails the job.
- The workflow's `permissions` are `contents: read`; a job widens them only for what it does.
- The `gate` job runs Postgres (`postgres:18.6`) and Mailpit (`axllent/mailpit` at an exact tag) as service containers with health checks, and passes `DATABASE_URL`, `SMTP_URL`, `MAILPIT_URL`, `MAIL_FROM` and `WEB_URL` to the gate. A new service joins that job, never a second workflow. A `services:` container takes no command, so the step before checkout turns off `fsync`, `synchronous_commit` and `full_page_writes` with `ALTER SYSTEM` and `pg_reload_conf()` (all three take a reload, no restart, so the health check that gated the job still holds) through `docker exec` on `job.services.postgres.id`, then reads `pg_settings` until all three read `off`, up to ten times a second apart, since `pg_reload_conf()` only signals the postmaster and returns before the reload lands, and fails after that. It reads no secret.
- The `changes` job decides the `android` job: full-history checkout without persisted credentials, then `.github/scripts/android-changed.sh <base> <head> .github/workflows/ci.yml` with `pull_request.base.sha` on a pull request and `github.event.before` on a push, `github.sha` as the head. It reads no secret. `gate` and `vercel` do not need it, so they run on every change.
- The `android` job is the Android leg of the gate (ADR 034), beside `gate` in the same workflow, and runs only when `changes` prints `true`: checkout, `actions/setup-java` (Temurin 17), `gradle/actions/setup-gradle` (Gradle cache and wrapper validation; the wrapper itself pins the Gradle version and its `distributionSha256Sum`), then in `apps/android` exactly `./gradlew detekt checkModuleBoundaries checkComposeFreeViewModels testDebugUnitTest assembleDebug`, the command `verification.md`'s `apps/android` row names. It uses the runner's preinstalled Android SDK and needs no service. Branch protection requires only `gate`, so a red `android` job does not block a merge on its own and a skipped one is not a failure; review reads it. The workflow's concurrency can cancel a `trunk` run's `android` job when a newer push skips it, which leaves that commit with the run from its pull request.
- The `vercel` job runs on `pull_request` only (on `push` to `trunk`, `deploy.yml` builds the same projects with `--prod`). It catches what the gate cannot see: Vercel's Hono detection, which needs the plain `Hono` value import in `apps/api/src/index.ts`, its type check of a TypeScript entry, and Nitro's Vercel output (ADR 031). Steps: a check that `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_API_PROJECT_ID` and `VERCEL_WEB_PROJECT_ID` are readable, failing with their names and never their values; then, before anything from the pull request is checked out, one pull step per project that runs `npx vercel@<exact version> pull --yes --environment=preview` in its own folder under `runner.temp` on the runner's preinstalled Node, prints the names of the pulled variables, deletes `.vercel/.env.*` and fails if the token was written to disk. Only these three steps see a `VERCEL_*` secret, so the pull request's code never runs while the token is in reach. Then checkout without persisted credentials, `pnpm install --frozen-lockfile`, and per project `pnpm dlx vercel@<exact version> build` with no token and no secret, its pulled `.vercel/` moved to the checkout root first and removed after; the api builds first, the web second with `NITRO_PRESET=vercel`. The build reads no environment variable: only the web's dev server and the api at runtime read `process.env`. The CLI version is the one `deploy.yml` pins. It never runs `vercel deploy` and never `--prod`, holds no `environment`, so it records no deployment, and needs no service. A pull request from a fork gets no secrets, so its `vercel` job fails at the check; the repo takes none. Branch protection does not require it.

## `deploy.yml`

- Trigger: `workflow_run` of `ci`, `completed`, on `trunk`. The `changes` job runs only when `vars.DEPLOY_ENABLED == 'true'`, the run's `conclusion` is `success`, its `event` is `push` and its `head_branch` is `trunk`; a `ci` run on a pull request also completes with `success`, so the event check is what keeps it out. With the variable unset, both jobs are skipped and the run is not a failure. `workflow_run` reads `deploy.yml` from the default branch, so a PR cannot exercise its own change to it.
- It deploys `github.event.workflow_run.head_sha`, never `github.sha`, which on `workflow_run` is the default branch's tip at trigger time.
- Tip guard: `changes` also requires `head_sha == github.sha`, so a run deploys only while the `ci` run it follows is still `trunk`'s tip. GitHub records the `production` deployment with `github.sha`, so the guard keeps every record equal to the commit that ran. Without it, two scenarios break. First, `ci` for A goes green and code push C lands before the deploy run is created: the record says C while production runs A, C's `ci` is then cancelled by docs push D (or fails), the C-to-D diff is docs-only, and C never ships. Second, re-running an old `trunk` `ci` run deploys an older commit, a silent rollback whose record names the tip, so later docs pushes are skipped. A superseded commit ships with the next green run, whose diff includes it.
- The workflow's concurrency group is `deploy` with `cancel-in-progress: false`: a newer green run waits for the running deploy and never cancels it halfway.
- Docs-only rule: `changes` reads the SHA of the newest `production` deployment that has a `success` status, then `.github/scripts/needs-deploy.sh <base> <head>` prints `false` only when every file in `git diff --no-renames --name-only <base> <head>` is under `docs/` or `apps/android/`, or ends in `.md`: neither the api nor the web builds from those paths, so an Android-only merge deploys nothing. No earlier deployment, a base the clone does not know, or an empty diff (a re-run) prints `true`. Diffing against the last deployment, not `github.event.before`, means a code push whose `ci` run was cancelled still deploys with the docs-only push that follows it. A docs-only skip creates no deployment, because only the `deploy` job holds `environment: production`.
- The `deploy` job runs in `environment: production` (ADR 031): checkout of `head_sha`, `pnpm install --frozen-lockfile`, then `vercel pull --environment=production` and `vercel build --prod` for the api project, its `.vercel/` moved aside to `.vercel-api/`, the same for the web project into `.vercel-web/` with `NITRO_PRESET=vercel` (Nitro's provider detection matches `GITHUB_ACTIONS` before `VERCEL` and would otherwise build the Node preset into `.output/`), then `pnpm --filter @mygame/api db:migrate` with `DATABASE_URL` set to the direct Neon URL, then `vercel deploy --prebuilt --prod` for the api and last for the web, each with its `.vercel/` moved back. Both projects build before anything touches the database, so a broken build migrates nothing, and a broken migration deploys nothing. The CLI is `pnpm dlx vercel@<exact version>`; `VERCEL_PROJECT_ID` is set per step, since `vercel pull` and `vercel deploy` read it. A build runs on the runner's Linux x64, so the function ships the `@node-rs/argon2` binary it loads.
- Secrets: `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_API_PROJECT_ID`, `VERCEL_WEB_PROJECT_ID` and `DIRECT_DATABASE_URL` (Neon's unpooled URL; the function reads the pooled one from Vercel's environment), passed through `env` and never echoed. Variable: `DEPLOY_ENABLED`. `changes` alone holds `deployments: read`.

## `android-changed.sh`

The one list of Android inputs, used by `ci.yml` and `app-distribution.yml`: `apps/android/**`, `apps/api/openapi.json` (the generated client) and `packages/catalog/**` (the generated `strings.xml`), plus the workflow file its caller names as the third argument. It prints `true` when `git diff --no-renames --name-only <base> <head>` holds one of them. An empty base, a zero SHA or a base the clone does not know prints `true`, since a missed Android build costs more than an extra one; an empty diff prints `false`. It reads no secret. Both callers check out full history, because in a shallow clone every base is unknown and the job would always run. Each caller assigns the output to a variable before writing `$GITHUB_OUTPUT`, so a script failure fails the step rather than writing an empty decision.

## `health.yml`

- Triggers: `schedule` at `0 6 * * *` (06:00 UTC) and `workflow_dispatch`. Both run the file on the default branch, so a PR cannot run its own change to it; `actionlint` is the check before merge.
- Guard: the one job, `status`, runs only while `vars.DEPLOY_ENABLED == 'true'`; otherwise it is skipped and the run is not a failure.
- Command: one `curl --fail` of `https://mygame.emm3000.com/api/health`, through the web's domain and its rewrite, so it checks the web, the rewrite and the api together; three retries, a 30 s limit. Anything but 200 fails the job, and GitHub's failed-run mail is the alert. It reads no secret.
- No `environment`. `environment: production` would record a `production` deployment at `github.sha`, which `deploy.yml`'s docs-only rule reads as the last deploy: a code commit whose deploy failed would then be skipped by the next docs-only push.
- Its own concurrency group, `health`. In the `deploy` group, GitHub keeps one pending run per group and cancels the older, so a queued health run could cancel a queued deploy.
- A change to `health.yml` alone counts as code for `needs-deploy.sh`, so its merge runs a full deploy. It stays code on purpose: a deploy is cheap and the rule stays one line.
- `permissions: contents: read` and a 5-minute timeout. It checks nothing out and uses no action.
- GitHub disables a public repo's schedules after 60 days without activity; `gh workflow enable health.yml` turns it back on.

## `app-distribution.yml`

- Triggers: `push` to `trunk` and `workflow_dispatch`, never `pull_request`, so a PR cannot run its own change to it; `actionlint` is the check before merge. The workflow starts on every `trunk` push rather than through `paths:`, which cannot read a script and would be a second copy of the list; the `changes` job then decides, and a push that changes no Android input ends there, with `build` and `distribute` skipped. `changes` runs only on `refs/heads/trunk`, so a dispatch on another branch distributes nothing.
- `changes` holds no secret: full-history checkout without persisted credentials, then `.github/scripts/android-changed.sh <github.event.before> <github.sha> .github/workflows/app-distribution.yml`. A `workflow_dispatch` has no `before`, so the script prints `true` and a dispatch always builds.
- Concurrency sits on the `build` job, group `app-distribution-<ref>-<decision>` with `cancel-in-progress: true`, never on the workflow. A newer building push cancels a superseded build, whose commits it contains. A workflow-level group would let a web-only push cancel an Android build and then skip its own, and that Android change would never reach the phone; the decision in the group name keeps a skipped job out of the building group. `distribute` is outside the group, so nothing cancels it halfway. A failed `build` is not retried by the next push: re-run it or dispatch.
- `build` holds no secret: checkout without persisted credentials, `actions/setup-java` (Temurin 17), `gradle/actions/setup-gradle`, then in `apps/android` `./gradlew assembleRelease` with `MYGAME_VERSION_CODE` set to `github.run_number`, so each build installs over the last. With no `MYGAME_RELEASE_*` setting it writes `app-release-unsigned.apk`, uploaded as the artifact `app-release-unsigned` (7 days).
- `distribute` needs `build` and runs no repo code: no checkout, no Gradle. It downloads the artifact, decodes `MYGAME_RELEASE_KEYSTORE_BASE64` to `$RUNNER_TEMP`, picks the runner's newest stable build tools (its own error when none exists, since the `grep` sits in `{ … || true; }` so `pipefail` cannot end the step first), aligns with `zipalign -P 16 -f 4` (16 KB pages for native libraries), signs with `apksigner` (passwords through `env:`, never the command line), verifies with `apksigner verify --print-certs`, prints the `versionCode` with `aapt2 dump badging`. Then `actions/setup-node` (Node 24, the SHA `ci.yml` pins; no checkout, so no `.node-version` to read), a step that writes `FIREBASE_SERVICE_ACCOUNT_JSON` to `$RUNNER_TEMP/service-account.json` under `umask 077`, and the upload: `npx --yes firebase-tools@<exact version> appdistribution:distribute dist/app-release.apk --app "$FIREBASE_APP_ID" --groups owner --release-notes "$RELEASE_NOTES"`, with `GOOGLE_APPLICATION_CREDENTIALS` pointing at the key file in that step only. The release notes name the commit and the run number and reach the CLI through the `RELEASE_NOTES` env var, never interpolated into the script, since a commit message is free text. A last `if: always()` step deletes the keystore and the key file.
- Secrets, each in the one step that needs it: `MYGAME_RELEASE_KEYSTORE_BASE64` in the decode step; `MYGAME_RELEASE_STORE_PASSWORD`, `MYGAME_RELEASE_KEY_ALIAS` and `MYGAME_RELEASE_KEY_PASSWORD` in the signing step; `FIREBASE_SERVICE_ACCOUNT_JSON` in the key-file step; `FIREBASE_APP_ID` in the upload step. A missing `MYGAME_RELEASE_*` secret or service-account JSON fails its step with its name, never its value.
- `firebase-tools` is pinned to an exact version at least two weeks old when chosen (`npm view firebase-tools time --json`), updated deliberately like an action SHA. The package ships no shrinkwrap, so its own dependencies resolve at install time; the CLI is pinned, its dependency tree is not.
- A change to `app-distribution.yml` alone counts as code for `needs-deploy.sh`, so its merge runs a full deploy, as `health.yml` does.

## Pinning

Third-party actions are pinned to a full commit SHA with the version tag in a trailing comment, updated deliberately. Never `@main`, never a tag alone, not even a major.

## Branch protection

`trunk` requires the `gate` check, a linear history and rebase merges only. Force pushes to `trunk` are refused by GitHub and by `.claude/settings.json`.

## What CI does not do

CI publishes nothing: no image, no release, no tag, no package; the `vercel` job builds and deploys nothing. The deploy to Vercel is its own workflow, as is the Android build sent to Firebase App Distribution (`app-distribution.yml`), each outside `ci.yml`'s concurrency group, so a newer push never cancels a deploy halfway (ADR 031).
